# 修改设置系统的计划

## 目前（修改前）的设置系统的工作原理

设置系统的核心文件：`src\ts\setting\Settings.ts`，它是一个前台脚本。

**打开标签页时加载设置：**

每当你打开一个 Pixiv.net 的标签页时，下载器都会读取最后一次保存的设置来使用。

**每个标签页里的设置互不影响：**

如果你在标签页 A 里做了一些修改，不会使标签页 B 里的设置发生变化。同样，如果你在 B 里做了修改，也不会使 A 里的设置发生变化。

有时这很有用，例如：
- 有时用户可能希望在不同标签页里使用不同的抓取条件或下载选项，所以每个标签页里的设置不会互相影响。
- 有些标签页里可能已经开始抓取或下载了，它们不该被其他标签页里的修改影响。

**只保存一份设置：**

下载器只会保存一份持久化的设置数据。

虽然你可以打开多个标签页并分别修改成不同的设置，但下载器不会为每个标签页分别保存一份设置。下载器只会储存一份设置。

PS：持久化的设置保存在浏览器扩展专用的本地存储区域里（`browser.storage.local`）。当你移除这个扩展时，浏览器会删除它保存的数据。

**保存最后一次修改的标签页里的设置：**

每当你在一个标签页里修改了设置，下载器就会保存这个标签页里的设置作为最新的设置数据。

如果你打开了多个标签页，并且分别修改了设置，那么最后一次修改是在哪个标签页里发生的，下载器就会保存哪个标签页里的设置。

需要注意的是：下载器保存设置时是以标签页为单位的。前面说过“每个标签页里的设置互不影响”，所以保存设置时也只会保存当前标签页里的设置，不会考虑其他标签页里的设置。

**旧的设置会被覆盖：**

下载器每次保存持久化设置时，都会覆盖之前的设置。有时这可能会让用户困惑。例如：

现在有两个已打开的标签页 A、B，它们使用相同的初始设置。然后你在标签页 A 里修改了选项 A，之后在标签页 B 里修改了选项 B。下载器会先保存标签页 A 的设置，然后保存标签页 B 的设置。

在最新的设置里，没有保存选项 A 的修改，只保存了选项 B 的修改。这是因为最新的设置就是标签页 B 的设置；标签页 A 里所做的修改已经被覆盖了。

**新的设置何时生效：**

当你在一个标签页里修改设置后，其他标签页不会受到影响。之后当你打开新的标签页，或者刷新标签页时才会使用最新设置：
- 打开新的标签页时，下载器会使用最新的设置
- 刷新已打开的标签页时，也会使用最新的设置

**导出设置：**

下载器在“更多”-其他分类里提供了导出和导入设置的功能。

你可以导出设置作为备份，也可以为不同的使用场景导出各自的配置文件，在需要时导入。

导出的设置会保存到一个 JSON 文件里。你可以修改它的文件名。

注意：当你导出设置时，导出的是当前标签页里的设置，而不是下载器储存的唯一一份持久化设置。这意味着，不管最新的设置是否已经发生了变化，你导出时的设置都是当前标签页里所看到的设置。

**导入设置：**

你可以选择下载器导出的设置文件进行导入。导入之后：
- 当前标签页里的设置会变成导入的设置，其他标签页不变。
- 下载器会立即保存导入的设置作为最新的持久化设置数据。之后打开或刷新的标签页会使用这份新的设置数据。

## 修改目标

目前设置系统的一个特点是：如果用户同时打开了多个 pixiv.net 的标签页，在其中一个标签页修改设置之后，其他标签页里不会变化。直到其他标签页刷新、或打开新的标签页时，由于会重新读取设置，所以才会应用变化。

**修改目标：**

当一个标签页里的设置变化时，会通知其他标签页，使它们可以接收新的设置，以便实时响应变化。

至于如何让其他标签页接收变化后的设置，我没有想好该怎么做。

**附加需求：**

添加一个设置项，允许用户选择使用旧版的行为或是新版的行为。设置名字是`当你修改设置时，其他标签页`，有两个单选按钮，一个是`同步变化`（默认值），另一个是`保持不变（旧版行为）`。如果用户选择`保持不变`，那么当一个标签页接收到来自其他标签页的设置变化时，不采用这个变化即可。

对于“同步变化 / 保持不变（旧版行为）”设置项：
- 情况 1: 当用户把设置从“同步变化”改为“保持不变”时，其他标签页里都会同步变成“保持不变”。这没有问题。
- 情况 2: 但当用户把设置从“保持不变”改为“同步变化”时，在其他标签页里，由于该设置之前的状态是“保持不变”，所以不会响应这次变化，所以其他标签页在没有刷新（重新加载设置）之前会始终保持为“保持不变”。
但是对于第二种情况，我觉得还是让其他标签页能相应变化更符合直觉一些。也就是这个设置项不管如何变化，都应该被其他标签页同步，并产生相应的效果。因此，这个开关的状态变化应该始终同步到所有标签页里。

另外，浏览器也可能回收闲置的前台页面，所以前台脚本每次初始化时都需要加载设置。目前已经有这个行为。

## 可行性分析（2026-08-04）

### 结论

修改目标可行，推荐使用 `browser.storage.onChanged` 同步设置，不需要把设置核心迁移到 Service Worker，也不建议使用 `window.postMessage`。

现有设置已经保存在 `browser.storage.local`，内容脚本也已有 `storage` 权限。因此当任意标签页把 `Config.settingStoreName` 写入本地存储后，其他标签页中的内容脚本可以通过 `browser.storage.onChanged` 收到变更，并把新的设置应用到各自的内存 `settings` 对象。新打开、刷新、或此前被浏览器回收的页面仍然沿用现有的 `restore()` 流程从存储加载最新设置，满足恢复场景。

### 现有实现与可复用基础

- `src/ts/setting/Settings.ts` 中的 `Settings` 实例由每个内容脚本独立创建；`restore()` 从 `browser.storage.local` 读取唯一的 `Config.settingStoreName`，然后通过 `assignSettings()` 和 `setSetting()` 恢复设置。
- 每次 `setSetting()` 都会派发 `EVT.list.settingChange`。`Settings` 已监听该事件，并以 50 ms 防抖把当前完整设置对象写入 `browser.storage.local`。
- 同一标签页中的各功能和设置表单已经监听 `settingChange`，所以接收端仍通过 `assignSettings()` / `setSetting()` 应用数据即可复用既有的类型转换、旧版兼容、设置副作用和 UI 刷新机制，不应直接替换 `settings` 对象。
- manifest 已声明 `storage` 权限。项目也同时支持 Manifest V3、Chrome 和 Firefox，`browser.storage.onChanged` 是适用于这些环境的 WebExtension 标准 API。

### 推荐方案：监听 storage 变更

在 `Settings` 中增加对 `browser.storage.onChanged` 的监听：

1. 仅处理 `areaName === 'local'` 且变更键为 `Config.settingStoreName` 的事件。
2. 读取变更后的完整设置对象；若它与当前标签页的设置等价，则不处理。这可以避免写入者收到自身变更通知时重复执行所有设置副作用。
3. 不要整体替换 `settings` 对象；逐项比较新对象和当前设置，只对有差异的项调用 `setSetting()`。这样既可沿用现有类型处理与兼容逻辑，也能避免一次普通修改在其他标签页触发所有设置项的副作用。
4. 应用远程设置期间设置一个内部标记，使这些由同步引起的 `settingChange` 事件不再次触发 `store()`。否则每个接收标签页都会把同一份设置重新写回存储，造成无意义的循环和大量事件。
5. 导入和重置不需要特殊的跨标签通信代码：它们本来就会逐项调用 `setSetting()`，最后由既有持久化逻辑写入存储；其他标签页收到最终存储变更后应用完整设置即可。

这是一种“以持久化设置为唯一同步源”的方案。它不依赖 Service Worker 的内存状态，因此 Service Worker 被回收不会影响同步；也不需要枚举标签页、维护连接或处理消息接收端不存在的错误。

### 不建议使用 window.postMessage

`window.postMessage` 的通信对象是具体的 `Window`，适合页面与 iframe、或已持有引用的窗口之间通信。普通内容脚本不能仅靠它枚举或可靠地向所有其他 Pixiv 标签页广播消息；即使通过网页同源机制或页面脚本间接实现，也会把扩展内部设置协议暴露给页面上下文，并引入来源校验、消息伪造和页面导航等额外问题。因此它不适合作为本需求的跨标签通信机制。

### Service Worker 转发方案的评估

Service Worker 方案同样可行。前台可通过 `runtime.sendMessage` 把变更发送到后台，后台使用 `tabs.query()` 和 `tabs.sendMessage()` 向 Pixiv 标签页转发。项目已有类似模式，例如关注列表和下载记录检查模块已经使用后台枚举 Pixiv 标签页并发送消息。

但该方案需要新增消息类型、消息校验、标签页筛选、发送失败处理、接收端防回传逻辑，并要确保 Service Worker 重启后不依赖易失内存。由于设置本来就必须持久化，最终仍要使用 `browser.storage.local` 作为恢复来源。相较于直接监听存储变更，它没有带来必要收益，代码范围和维护成本更高。

### 一致性与行为边界

- 目前的 50 ms 防抖会合并同一标签页连续发生的设置修改；其他标签页在写入完成后收到一份完整的新快照，而不是每个字段都逐条同步。这符合当前“完整设置对象持久化”的数据结构。
- 正常顺序操作中，标签页 A 修改选项后，标签页 B 会更新；随后 B 的再次修改会基于已同步的数据保存，能够避免原有的常见覆盖问题。
- 如果两个标签页在彼此尚未收到同步结果时几乎同时修改，仍可能发生“最后写入者胜出”的冲突：因为当前存储单元是一整个设置对象。该问题不是跨标签通知本身能够完全消除的。若将来需要强一致合并，应另行设计按字段存储、版本号/修订号或后台串行合并机制；本次目标不需要为此进行大规模数据结构迁移。
- 运行中的抓取和下载会接收到新的 `settingChange` 事件。现有模块已可选择监听特定设置并实时响应；是否在任务开始后冻结某类设置属于各模块既有行为，应保持不变，不应由同步层强行暂停或重启任务。

### 对附加需求的影响

新增“同步变化 / 保持不变（旧版行为）”设置项是兼容的。该选项本身仍应正常保存和同步；接收端在处理其他标签页写入的设置快照前，依据本标签页当前的行为选项决定是否调用 `assignSettings()`。默认值设为“同步变化”即可。

如何处理“同步变化 / 保持不变（旧版行为）”的开关：
这个开关应作为始终同步的控制项，不受自身“保持不变”状态限制。
接收端收到设置快照后，先检查该开关是否发生变化：若变化，则始终应用完整快照；若未变化且本地为“保持不变”，才忽略该快照。这样从“保持不变”切回“同步变化”时，所有标签页会立刻恢复同步，并应用这份最新设置。

### 复盘补充：接收和应用快照的细节

`storage.onChanged` 提供的是整个设置对象的变更，但接收端不应每次都对对象中的每个字段调用 `setSetting()`。目前不少模块监听 `settingChange` 并立即执行功能；如果用户只修改一个选项，却在每个其他标签页里重新派发所有设置项的事件，会造成不必要的界面刷新、功能重复初始化和性能开销。

因此，接收端应按以下顺序处理快照：

1. 验证 `changes[Config.settingStoreName].newValue` 存在且是设置对象。
2. 先比较新快照中的“其他标签页的设置同步方式”和本标签页的当前值。这个字段的差异必须始终应用，不受本地“保持不变”限制；切换为“同步变化”时，应将该快照作为最新完整设置一并应用。
3. 如果同步方式未变化且本标签页选择“保持不变（旧版行为）”，忽略该快照。
4. 在允许同步时，逐项比较新快照与当前 `settings`；只对确有差异的项调用 `setSetting()`。比较时需要使用深度比较，以正确处理数组和对象设置。
5. 在上述应用期间启用“正在应用远程设置”的内部标记，阻止 `settingChange` 的存储监听器再次写入 `browser.storage.local`；完成后无论成功与否都必须清除该标记。

逐项调用 `setSetting()` 仍然保留了设置类型转换、兼容旧设置和事件通知。若新快照缺少当前版本新增的设置项，应保持本标签页的默认值，而不是把缺失项清空。源标签页写入后若也收到了 `storage.onChanged`，由于所有字段均相同，应直接跳过，避免重复执行副作用。

“保持不变”期间，用户仍可在该标签页修改设置并保存；这些修改会成为新的持久化快照，但其他同样处于“保持不变”的标签页不会采用它。当任一标签页把同步方式切回“同步变化”时，其当前完整快照将成为所有标签页立即采用的最新设置。这是全局持久化同步开关的自然结果，也与刷新或新开标签页会加载该最新快照的行为一致。

### 建议验收场景

1. 两个已打开标签页均为“同步变化”时，在 A 修改单个设置，确认 B 的对应功能和表单实时更新，且 B 不会重复写回设置。
2. 两个标签页均变为“保持不变（旧版行为）”后，在 A 修改普通设置，确认 B 不更新；将 A 的同步方式改回“同步变化”后，确认 B 立即恢复为 A 的完整最新设置。
3. 在 A 导入设置或重置设置，确认 B 接收最终快照，且只对实际变化的设置项产生响应。
4. 在同步方式为任意值时刷新或新开标签页，确认页面始终从 `browser.storage.local` 加载最新持久化快照。
5. 两个标签页近乎同时修改不同设置，确认结果符合“最后写入者胜出”的既定边界，且不会形成存储写入循环。
