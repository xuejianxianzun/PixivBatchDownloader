# 适配用户主页的约稿分类页面

## 情况说明

有些用户会接受约稿，并且可能有为了约稿而创作的作品。这些约稿的内容会显示在用户主页的“约稿”分类里（路径是 `/request`。

### 示例用户

用户 1 的约稿主页网址：
https://www.pixiv.net/users/42787448/request
其中 `42787448` 是该用户的 ID。

里面有多个子页面，分别有不同的网址：
- 可选择的约稿方案：https://www.pixiv.net/request/plans/94805
- 查看该用户已接受（正在创作中的）某个约稿申请：https://www.pixiv.net/requests/389567
- 查看该用户已接受的所有约稿申请：https://www.pixiv.net/users/42787448/request/in_progress
- 查看该用户创作的约稿作品（图片分类）：https://www.pixiv.net/users/42787448/request/artworks
- 约到的作品（该用户向别人发起的约稿）：https://www.pixiv.net/users/42787448/request/sent
- 约到的图片作品：https://www.pixiv.net/users/42787448/request/sent/artworks

在这些子页面里，有些是约稿方案、进行中的约稿，这些不是作品信息，不需要处理。

上面这个用户是创作插画/漫画的，下面这个用户 2 是创作小说的，他的约稿主页网址：
https://www.pixiv.net/users/50655624/request

查看该用户创作的小说约稿作品：
https://www.pixiv.net/users/50655624/request/novels

### 适配目标

适配约稿分类页面的**重点是获取作品信息**。主要分为两种情况：
1. 该用户创作的约稿作品（别人向该用户发起的约稿），分为 `/request`、`/request/artworks` 和 `/request/novels` 页面。
2. 约到的稿（该用户向别人发起的约稿），分为 `/request/sent`、`/request/sent/artworks`、`/request/sent/novels` 页面。

备注：
- `/request/artworks`、`/request/sent/artworks` 里包含了所有图片类型的作品：插画、漫画、动图。所以没有 `/request/sent/manga` 和 `/request/sent/ugoira` 这样的网址。
- 在约稿作品列表页面里，不会根据作品的标签列表来划分子页面，也就是说 `/request/artworks`、`/request/novels`、`/request/sent/artworks`、`/request/sent/novels` 就是路径的最后一层，后面不会再有别的路径层级。
- 在约稿作品列表页面里，作品是无限滚动加载的，因此没有分页的页码。这个用户有 105 个约稿作品：https://www.pixiv.net/users/9459043/request/artworks 可以验证这一点

## 通过 API 获取所有约稿作品的数据

### 获取该用户创作的约稿作品

首先需要使用第一个 API 获取约稿页面的详细数据：

https://www.pixiv.net/ajax/commission/page/users/9459043/request?lang=zh

这个 API 的 `body.page` 里包含了约稿页面的主要数据，例如：
- `plans`：可选择的约稿方案。类型是对象数组，不过内容我不关心
- `inProgressRequestIds`：正在创作中的约稿，类型是 `string[]`
- `postArtworkRequestIds`：该用户创作（已发表）的约稿作品（图像分类），类型是 `string[]`
- `postArtworkCount`：该用户创作（已发表）的约稿作品的总数（图像分类），类型是 `number`
- `postNovelRequestIds`：该用户创作（已发表）的约稿作品（小说分类），类型是 `string[]`
- `postNovelCount`：该用户创作（已发表）的约稿作品的总数（小说分类），类型是 `number`

注意：
- `postArtworkRequestIds`、`postNovelRequestIds` 里保存的都不是作品 ID，而是这个作品的约稿 ID。
- 虽然在 `body.thumbnails.illust` 或 `body.thumbnails.novel` 里有一些作品数据，但最多只有 12 项，这是因为在约稿主页（`/request`）页面里，每种类型的作品最多只会显示 12 个。另外，由于这些作品数据里没有包含约稿 ID，所以无法把约稿 ID 与作品数据对应起来。所以不应该直接使用这些作品数据。

点击作品列表下方的“查看全部”按钮会进入 `/request/artworks` 或 `/request/novels` 页面，会显示所有约稿作品。

这个页面里会使用第二个 API，传递约稿 ID 来获取作品的较为详细的数据。示例：

```
https://www.pixiv.net/ajax/commission/requests?requestIds[]=224149&requestIds[]=223538&requestIds[]=221034&requestIds[]=211841&requestIds[]=212052&requestIds[]=198087&requestIds[]=205507&requestIds[]=201591&requestIds[]=199880&requestIds[]=196014&requestIds[]=195834&requestIds[]=183332&requestIds[]=183334&requestIds[]=179320&requestIds[]=176538&requestIds[]=173269&requestIds[]=163542&requestIds[]=165688&requestIds[]=161619&requestIds[]=162050&requestIds[]=161989&requestIds[]=162048&requestIds[]=154056&requestIds[]=144760&lang=zh
```

在返回的数据里，`body.thumbnails.illust` 或 `body.thumbnails.novel` 里包含本次请求里所有作品的数据。`body.thumbnails.illust` 里的数据类型是 `ArtworkCommonData[]`， `body.thumbnails.novel` 里的数据类型是 `NovelCommonData[]`。这只是中等详细程度的数据，不是最完整的数据，例如没有包含收藏数量 `bookmarkCount`。从这些数据中提取作品 ID 生成 IDData 数据，之后就可以开始抓取每个作品的详细数据了。

备注：
- 这个 API 限制了单次请求中最多只能传递 50 个 `requestIds[]`。超过 50 个就会产生 400 错误，提示“不正确的请求”。
- 这个 API 的参数里没有区分作品类型（插画或小说），看来 requestIds 是不会重复的，所以无需区分类型。

### 获取该用户约到的稿

和上面类似，也需要使用两步 API。首先请求这个 API 获取该用户“约到的稿”的详细信息：

https://www.pixiv.net/ajax/commission/page/users/42787448/request/sent?lang=zh

这个 API 的 `body.page` 里包含了约稿页面的主要数据，例如：
- `sentArtworkRequestIds`：该用户创作（已发表）的约稿作品（图像分类），类型是 `string[]`
- `sentArtworkCount`：该用户创作（已发表）的约稿作品的总数（图像分类），类型是 `number`
- `sentNovelRequestIds`：该用户创作（已发表）的约稿作品（小说分类），类型是 `string[]`
- `sentNovelCount`：该用户创作（已发表）的约稿作品的总数（小说分类），类型是 `number`

注意：`postArtworkRequestIds`、`postNovelRequestIds` 里保存的都不是作品 ID，而是这个作品的约稿 ID。`body.thumbnails` 里同样也最多只有 12 个作品的数据。

之后使用第二个 API，传递约稿 ID 来获取作品的较为详细的数据。示例：

```
https://www.pixiv.net/ajax/commission/requests?requestIds[]=182117&requestIds[]=185016&requestIds[]=188314&requestIds[]=183867&requestIds[]=181947&lang=zh
```

这里的第二个 API 和上面的第二个 API 是相同的。

## 实施计划

鉴于约稿页面里的 API 和抓取流程与用户主页所使用的 API 有所不同，因此更适合把约稿页面作为一个新的、独立的页面类型，单独处理，而不是把它视为用户主页。

我已经在 `src\ts\crawlMixedPage\InitUserRequestPage.ts` 实现了这个功能。

-------

测试过程中发现的一些现象：

1. 在抓取“约到的稿”时，抓取到的作品数量可能比显示的数量少。在这个页面里：

https://www.pixiv.net/users/42787448/request/sent/artworks

显示的总数有 17 个，但是页面上只显示了 16 个，API 返回的也只有 16 个。这不需要特别处理。

2. 当抓取数量小于投稿的作品数量时，下载器会从所有投稿作品的 ID 里裁切出最前面（近期）的作品。另外，如果一个用户同时有约稿的图片作品和小说作品，下载器会先把两者的投稿 ID 合并（图片作品的 ID 在前面），然后裁切，这会导致优先保留图片作品。这是符合预期的，因为在网页上，图片作品列表会显示在前面，小说列表显示在后面。虽然也可以考虑更公平的处理方法：把图片和小说的投稿 ID 混合后先倒序排列，然后裁剪，这样获得的就是从时间上最近的作品，而不是图片优先。但是目前没必要这么做。
