# 下载文件出错或失败时的处理机制

相关模块：`src/ts/download/Download.ts`、`src/ts/download/DownloadControl.ts`、`src/ts/download/DownloadStates.ts`、`src/ts/serviceWorker/background.ts`、`src/ts/store/States.ts`、`src/ts/Config.ts`。

> 本文调研于 2026-09-09，针对「内容脚本里下载远程图片文件（而非动态生成的 Blob url）时，下载失败是否有重试措施」的问题。

下载器对下载失败的处理是**三层递进的重试机制**：单文件内的 Fetch 级重试 → 批级整体重试 → 浏览器保存文件失败的重新下载。每一层失败都有对应的兜底策略。

# 总览

```
远程图片下载失败
  │
  ├─ 第一层  Download.download() 内 Fetch 级重试（上限 Config.retryMax = 10 次）
  │     │
  │     ├─ 重试打满后 afterReTryMax(status) 按状态码分流：
  │     │     ├─ 404 / 500            → skipDownload 跳过，不再重试（不阻塞下载流）
  │     │     ├─ 0 + 间隔短           → 判定磁盘空间不足 → 弹窗提示 + 暂停
  │     │     └─ 其他（403/429/502…） → 记日志 + 触发 downloadError 事件
  │     │                                  │
  │     └─────────────────────────────────┘
  │
  ├─ 第二层  DownloadControl 批级整体重试（无次数上限，直到成功或用户停止）
  │     所有任务结束且存在失败项时：暂停 → 等待 2 秒 → startDownload()
  │     → downloadStates.resume() 只把失败项（状态 0）复位为未开始（-1）
  │     → 成功文件绝不重复下载
  │
  └─ 第三层  浏览器保存文件失败（download_err，来自 background.ts）
        ├─ USER_CANCELED（用户取消另存为 / IDM 接管）→ 跳过，不再重试
        └─ 其他错误（FILE_FAILED 等）→ saveFileError()：等待 3 秒 → 复位任务状态 → 重新下载
```

# 第一层：单文件内的 Fetch 级重试（Download.ts）

内容脚本下载远程图片的核心在 `Download.download()`（Download.ts 约 103 行）。整个 fetch + 读流在 try/catch 里，凡是下述异常都会进入 catch 并**递归重试整次下载**：

- **网络层失败**：`fetch` 抛 `TypeError`（断网、代理问题、超时），此时 `status` 记为 0；
- **HTTP 非 2xx**：`!response.ok` 时显式 `throw new Error('HTTP error ' + status)`；
- **读响应体中途断流**：`reader.read()` reject（下载到一半断网也覆盖）。

**重试上限**：`Config.retryMax = 10`（Config.ts 约 15 行），即一个文件一轮最多发起 10 次请求。每轮重试前会走 `downloadInterval` 的请求间隔节流（有设置项可调）。

**不重试的情况**：主动取消（`AbortError`、用户停止）。

# 重试打满后的分派：afterReTryMax(status)

下载重试打满 10 次后，按状态码分流（Download.ts 约 298 行）：

| 状态 | 处理 | 是否会再自动重试 |
| --- | --- | --- |
| **404 / 500** | 确定性错误，`skipDownload` 直接跳过并记日志「不会再重试下载它」 | 不重试（计入跳过，不阻塞下载流） |
| **0 + 10 次中 9 次间隔 ≤ 10s** | 判定磁盘空间不足，弹窗提示 + 触发暂停 | 暂停等用户处理（避免死循环刷请求） |
| **其他**（403/429/502、间隔长的超时等） | 记日志「暂时跳过它并在其他文件下载完毕后重试下载它」，触发 `downloadError` 事件 | 进入第二层 |

# 第二层：批级整体重试（DownloadControl.ts）

`downloadError(id)` 把失败 id 收进 `errorIdList`（DownloadControl.ts 约 568 行；该列表语义：指 Download 模块内文件下载失败，**不是**浏览器保存文件的失败），然后继续下载其余文件，把失败项留在队列末尾。

当**所有任务结束且存在失败项**时（`downloaded + errorIdList.length === total`），触发 `checkCompleteWithError()`（DownloadControl.ts 约 716 行）：

```
暂停下载 → 日志「稍后会重试下载失败的文件」→ 等待 2 秒 → startDownload()
```

关键设计是重入方式：`pause` 状态下 `startDownload` 走 `downloadStates.resume()`（DownloadStates.ts 约 53 行）——**只把失败的项（状态 0）复位成「未开始」（-1），已成功的项（状态 1）保持不动**，随后线程只挑选这些失败文件重新下载。也就是说：**每次整批重试只补下失败的文件，成功文件绝不重复下载**。

注意：**这一层没有次数上限**。若网络持续故障，会「每批失败 → 隔 2 秒 → 再来一批」循环往复（每个文件每批又打满 10 次请求）。这是「尽力而为、直到成功或用户干预」的设计——用户可随时点停止/暂停打断；404/500 与磁盘不足已在上层排除出循环。

# 第三层：浏览器保存文件失败（download_err，后台）

这一层不是网络下载失败，但同属完整链路：Service Worker 里 `downloads.onChanged` 检测到下载项 error 时（background.ts 约 242 行），会**先把该 id 从去重列表里移除**（这样前台重试时不会被判定为重复任务而拦截），再回传 `download_err`。前台收到后（DownloadControl.ts 约 223 行）：

- `USER_CANCELED`（用户取消另存为、IDM 接管）→ 跳过，不再重试；
- 其他错误（`FILE_FAILED` 等）→ `saveFileError()`（DownloadControl.ts 约 634 行）：等待 3 秒 → 复位该任务状态 → 重新下载。同样无显式次数上限，每次失败隔 3 秒重试一次。

# 其他保护：长时间无回执的 watchdog

**300 秒无回执 watchdog**（DownloadControl.ts 约 149 行）：发出保存请求后 5 分钟没收到浏览器回执（典型如「另存为」对话框一直挂着），只弹「可能发生了错误/下载卡住」的提示，**不自动重试**，因为这种情况重试无意义。

# 一句话总结

对「网络链路问题导致远程图片下载失败」，设计是 **文件内 10 次快速重试 → 收尾 2 秒后整批自动补下（无上限，直到成功或用户停止）**，404/500 与磁盘不足等「重试也白搭」的情形会被识别并排除，成功文件在补下轮次中不会被重复下载。
