# 添加抓取用户列表的功能

我想添加一个“抓取用户列表”的功能。需要为它单独添加一个模块，保存到 `src/ts/crawlMixedPage/CrawlUserList.ts`。

该模块并不属于某个特定的页面类型，也不继承其他模块。但是需要从其他模块里借鉴一些处理逻辑，下面会说明。

该模块提供公共方法入口，可以由其他模块调用。

在 `src/ts/crawlMixedPage/InitHomePage.ts` 的抓取列表的最前面添加一个抓取按钮，按钮上的文字就是“抓取用户列表”，点击之后会调用这个模块。

工作流程如下：

## 1. 预检查

先检查 states.busy，如果在忙就显示提示 `toast.error(lang.transl('_当前任务尚未完成'))`，然后返回，不执行。

如果不忙，则检查是否有缓存的未完成的任务数据。如果有的话用弹窗询问用户：`检测到有未完成的“抓取用户列表
”任务，要恢复该任务吗？`，如果用户选择确定，则进入恢复任务的流程；否则继续往下走。

## 2. 输入用户 ID 列表

如果不忙，就调用 Input 组件让用户可以输入用户列表。此处的逻辑可以参考 InitHomePage 里的 `inputIDList` 方法。其 `instruction` 参数（提示）为：

```html
请输入用户 ID 列表，每个 ID 之间以换行分隔（即每行一个 ID）。<br><br>
提示：<br>
- 这个功能是为一次性抓取多个用户而设计的。如果你只需要下载一个用户的作品，可以进入他的主页并开始抓取。<br>
- 如果你需要设置一些筛选条件（如作品类型、收藏数量、时间范围、标签），请先进行设置，然后再开始抓取。<br>
- 请确认在“抓取完成后，自动开始下载”设置里勾选了“快速下载任务”，否则下载器不会自动开始下载。<br>
- 在执行过程中，不要在这个标签页里执行其他抓取任务。如果有需要，你可以打开新的 Pixiv 标签页进行浏览和下载。<br>
- 在执行过程中，如果你不小心关闭了这个网页，可以重新进入该页面，并点击“抓取用户列表”按钮来恢复进度。<br>
- 在执行过程中，如果你想放弃（终止）该任务，可以点击“停止抓取”按钮。该任务会立即终止，并且不能从中断处恢复。
```

`placeholder` 参数为 `163536\n12539859\n1980643\n28172249\n73117898`。

在检查时去重，并要求全部是数字，如果有不是数字的内容就使用轻提示`toast.error`显示“用户 ID 必须全部是数字”并返回。如果没有输入任何内容也返回。

## 3. 输入抓取的作品数量

在用户输入了有效的 ID 列表之后，显示一个 Input 组件。这次可以参考 `crawlIdRange` 方法，显示单行输入框。其 `instruction` 参数（提示）为：

```html
你想从每个用户那里抓取多少个作品？<br><br>
提示：<br>
- 下载器会从最新的作品开始抓取，即按作品 ID 从大到小抓取。<br>
- 如果你只想抓取部分作品，可以输入具体的数字；<br>
- 如果你想抓取所有作品，可以输入 <span class="blue">-1</span> 或者一个很大的数字。<br>
```

`placeholder` 参数为 `-1`。

在检查时把值格式化为整数（parseInt），并要求这个值：
- 是有效的数字
- 不能是 0，只能小于 0 或者大于 0
- 如果小于 0，只能用 `-1`
如果不满足要求就使用轻提示`toast.error`显示“数字必须设置为 -1 或者大于 0”，然后返回。

## 4. 抓取和下载

上面两个输入框都满足要求之后，才会把两次输入的值实际保存到自己的变量上，并准备开始抓取。

如果抓取数量是 `-1`，则把内部的抓取数量设置为最大值 `crawlWorksNumber = Config.worksNumberLimit`，否则设置为用户设置的值。

需要保存任务队列、进度。

以用户为单位抓取、下载。一个用户的作品下载完了，再开始处理下一个用户的抓取、下载流程。

还需要在日志里显示提示，下面我会进行说明。

### 总是慢速抓取

该模块总是使用慢速抓取。它不需要修改公用的慢速抓取的标记 `states.slowCrawlMode`，只需要在自己内部使用慢速抓取的逻辑即可。

在抓取过程中使用串行发送请求，并且每次请求之间使用间隔时间（除非有缓存可用）：

```ts
await Utils.sleep(settings.slowCrawlDealy)
```

### 任务开始时的日志

任务初始化之后，显示一条轻提示（`toast.show`），内容是“开始抓取用户列表”。

然后显示如下的日志：（日志里包含备注，括号和备注不需要显示到日志里）

```md
🚀开始抓取用户列表（备注：这条使用绿色，也就是 log.success 方法）
一共有 {x} 个用户 ID
从每个用户那里抓取{数量}作品（备注：如果 `crawlWorksNumber === Config.worksNumberLimit`，数量就显示为`所有`；否则就显示为` {crawlWorksNumber} 个 `。
{慢速抓取的提示}（备注：这条复用已有的语句，`log.warning(lang.transl('_慢速抓取'))`）（备注：这条使用 2 个换行，方式是在这条之后额外输出一条空日志 `log.log('')`）
```

### 每次循环的详细步骤

每次循环指的是从抓取一个用户、到该用户处理完毕的流程。

在每次循环开始时，都设置 `states.busy = true`，并设置快速抓取状态 `states.quickCrawl = true`。

#### 获取 ID 列表

先根据用户 ID 获取一次他的用户名（使用 `API.getUserProfile` 方法），以便在日志里显示。日志为：

```md
开始抓取 {用户链接} 的作品，用户 ID 为 {ID}（备注：这条消息是绿色的；用户链接使用 `Tools.createUserLink` 方法生成）
他在队列中的位置是 {进度}（备注：这条消息是绿色的；进度是他在整个用户列表里的编号，从 1 开始，如 `1/10`）
开始获取作品列表
```

接下来：

- 调用 `API.getUserWorksByType()` 方法，只传递用户 ID，就可以获取用户的所有作品的 ID 列表。
- 按照 ID 从大到小排列（因为之前的提示里说了“下载器会从最新的作品开始抓取，即按作品 ID 从大到小抓取”）。
- 如果抓取数量小于作品总数量，就裁剪，留下等于抓取数量的 ID 列表。
- 把保留的 ID 列表保存到 `store.idList` 里（直接覆写）。
- 触发 `getIdListFinished` 的流程。具体步骤参考 `src/ts/crawl/InitPageBase.ts` 里的 `getIdListFinished` 方法，主要复用：
  - 预先对 id 进行检查
  - `log.log(lang.transl('_当前有x个作品', store.idList.length.toString()))`
  - 处理 `// 导出 ID 列表，并停止抓取` 的逻辑。如果它的判断条件为真，那么在导出 ID 列表之后，这个用户的处理流程就结束了，在这里返回，然后开始处理下一个用户。注意：这部分的代码里面不要触发 `stopCrawl` 事件，否则会停掉整个抓取用户列表的任务。
  - `log.log(lang.transl('_开始获取作品信息'))`
- 进入下面的“获取每个作品的数据”步骤。

#### 获取每个作品的数据

- 获取每个作品的详细数据。具体步骤参考 `src/ts/crawl/InitPageBase.ts` 的 `getWorksData`，很多逻辑是相同的，包括取 ID、对 id 进行检查、根据作品类型进行处理。但本模块的抓取里没有 `idData.type === 'novelSeries'` 的情况，只有普通的单个作品；也不需要设置 `this.mergedNovelCount`。
- 每当处理完一个作品的详细数据，就参考 `afterGetWorksData` 方法处理。不需要“会员搜索优化策略”的部分；它里面有一个分支 `if (states.slowCrawlMode)`，作用是“根据慢速抓取设置，决定是否添加间隔时间”，但在本模块里去掉这个判断，始终添加间隔时间。保留“有缓存时不使用间隔时间”的处理。
- 当所有作品都处理完毕后，参考 `crawlFinished` 方法，基本可以完全复用其逻辑。包括其调用的 `noResult` 方法，也可以复用大部分（只需要去掉处理 `this.mergedNovelCount` 的部分）。这部分会触发一些事件，正常触发即可。

#### 抓取完成后

在 `crawlFinished` 方法执行完毕之后，根据有无抓取结果处理：
- 如果没有抓取结果，那么这个用户的处理就完成了，可以开始抓取下一个用户了。
- 如果有抓取结果，`src/ts/download/DownloadControl.ts` 模块会执行 `readyDownload` 方法，并进入“// 处理快速下载任务”的分支。此时：
  - 如果可以自动开始下载，那么下载模块会在下载完成后触发事件 `EVT.fire('downloadComplete')`，这个用户的处理就完成了。
  - 如果不可以自动开始下载，那么可能一直都不会触发下载完成的事件。不需要特别处理。

### 任务执行完毕

显示轻提示（`toast.success`），内容为“抓取用户列表完毕”。

显示绿色的日志：

```md
✅抓取用户列表完毕（备注：使用 2 个换行）
```

清除缓存的任务数据，并复位循环开始时的状态。

## 用户可以停止任务

在开始抓取之后，显示“停止抓取”按钮 `stopCrawling`。用户点击它之后，停止该任务，并显示红色的轻提示和日志：

已停止抓取用户列表

```md
🛑已停止抓取用户列表
```

清除缓存的任务数据，并复位循环开始时的状态。

## 防止用户误操作

### 缓存任务数据

在本地存储 `localStorage` 里保存进度，只需要保存用户 ID 列表、抓取数量、处理进度（只需要记录正在处理哪个用户的进度（索引），不需要记录抓取进度或下载进度）。

这份数据全局唯一，不区分批次。新开始的任务的数据可以覆盖旧的数据。

在用户停止任务、任务执行完毕之后，清除缓存的任务数据。

### 恢复任务的流程

不主动恢复任务，只有在预检查步骤里，通过用户确认才会恢复任务。

如果用户确认时，下载器正忙（可能在抓取或下载），则使用消息框显示提示。消息框的标题是“抓取用户列表”，下同。消息是：

```html
下载器正忙，可能正在抓取或下载，所以无法恢复未完成的“抓取用户列表”任务。<br>
你可以停止当前进行中的任务，或者等任务完成后重试该操作。
```

然后返回，不恢复任务。

如果下载器不忙，则恢复任务。之后执行：
- 在日志里显示“任务开始时的日志”章节里的日志
- 使用消息框 `msgBox.show`显示提示，消息是：
```html
已恢复之前的任务。<br>下载器会从之前正在处理的那个用户开始，重新进入抓取和下载流程。<br>如果你之前已经下载了他的一些文件，可以启用“不下载重复文件”功能，以避免下载重复的文件。
```
- 找到之前正在处理的那个用户，从他开始进入“每次循环的详细步骤”的流程。该用户之前的状态是正在处理，可能当时已经有一些抓取或下载进度了，现在舍弃，重新开始抓取。

### 防止用户不小心关闭页面的提示

在抓取所有用户的任务未全部完成之前，如果用户要关闭/刷新标签页，则显示提示。因此需要绑定 `window.onbeforeunload` 的事件，并使用 Msgbox 显示消息，内容为`抓取用户列表的任务尚未完成。如果你确实想放弃任务，请点击下载器设置面板里的“停止抓取”按钮。`。用户如果取消关闭页面的话，就会看到这个消息。

可以参考 `src/ts/SelectWork.ts` 里的 `window.onbeforeunload` 处理。但这里有个问题：`window.onbeforeunload` 上应该只能注册一个回调，所以本模块的回调会覆盖其余的回调。如果使用注册事件的方式的话，可能不会生效（参考 SelectWork 里的注释）。

# 实现

（2026-10-14。本节描述该功能当前的完整工作流程。）

功能实现在 `src/ts/crawlMixedPage/CrawlUserList.ts`（单例 `crawlUserList`，公开入口 `ready()`）。它不属于某个页面类型、也不继承其他模块，抓取流程复用了 `InitPageBase` 的实现（裁剪版）。

一句话概括：在首页输入多个用户 ID 和每个用户的抓取数量后，下载器按用户逐个抓取、下载；一个用户**下载完毕**（或用户放弃下载）之后，才会开始处理下一个用户。

```
点击首页的「抓取用户列表」按钮
→ 预检查（是否忙碌 / 有无未完成任务要恢复）
→ 输入用户 ID 列表 → 输入抓取数量
→ 任务开始（日志、缓存任务数据、阻止关闭页面）
→ 【循环】每个用户一轮：
    轮开始（crawlStart：重置 store、复位下载模块、显示停止按钮）
    → 用户级预检查 → 获取用户名 → 获取作品 ID 列表
    → 逐个抓取作品数据 → 抓取完毕（crawlComplete）
    → 等待本轮下载结束 → 下一个用户
→ 所有用户处理完 → ✅完成（或中途点「停止抓取」→ 🛑停止）
```

## 1. 入口与预检查

首页的「抓取用户列表」按钮点击后调用 `crawlUserList.ready()`：

1. 先触发 `closeSettingsPanel`，关闭设置面板。
2. 检查 `states.busy`。如果下载器正忙，轻提示「当前任务尚未完成」，直接返回。
3. 检查 localStorage 里有没有未完成的任务数据（键名 `crawlUserListTask`）。如果有，用 `window.confirm` 询问是否恢复：
   - 点确定 → 走「恢复任务」流程（见「6. 恢复任务」）；
   - 点取消 → 继续按新任务处理。

## 2. 输入

**用户 ID 列表**：多行输入框（6 行高），提示与 placeholder 见前文《2. 输入用户 ID 列表》。校验：

- 内容为空、或按行拆分去掉空行后为空 → 轻提示「本次操作已取消」，返回；
- 任意一行不是纯数字（`/^\d+$/`）→ 轻提示「用户 ID 必须全部是数字」，返回；
- 通过后去重，得到最终的用户 ID 列表。

**抓取数量**：单行输入框（默认值与 placeholder 都是 `-1`），提示见前文《3. 输入抓取的作品数量》。校验：`parseInt` 后必须是有效数字，且只能是 `-1`（表示抓取所有作品）或大于 0，否则轻提示「数字必须设置为 -1 或者大于 0」并返回。通过后，`-1` 在内部换算为 `Config.worksNumberLimit`。

两个输入都通过后，**再检查一次 `states.busy`**（输入期间下载器可能又忙了），然后才把值保存到模块变量。

## 3. 任务开始

1. 清空日志区，轻提示「开始抓取用户列表」，输出任务开始日志：
   - 🚀开始抓取用户列表（绿色）
   - 一共有 {x} 个用户 ID
   - 从每个用户那里抓取所有作品（或：从每个用户那里抓取 {x} 个作品）
   - 「慢速抓取，以避免触发 429 限制」（黄色）+ 一行空行
2. `startRun()` 做准备工作：
   - `states.crawlUserList = true`；重置 `states.stopCrawl = false`（这个标记会一直保持 true 到下一次任务开始，所以任务开始时必须自己重置）；
   - 把任务数据写入 localStorage；
   - 包裹 `window.onbeforeunload`（任务完成前阻止用户关闭/刷新页面）；
   - `await mute.getMuteSettings()` 预取屏蔽设定（供每轮的用户级预检查用）；
   - 进入用户循环。

## 4. 用户循环（一轮 = 一个用户）

### 4.1 轮开始

- 更新 `progressIndex` 并写入 localStorage（记录正在处理哪个用户，用于恢复）。
- 设置 `states.busy = true`、`states.quickCrawl = true`，然后**触发 `crawlStart` 事件**。这是每轮的关键一步，它一次性完成：
  - 重置 `store`——必须每轮重置，否则上一个用户的抓取结果会残留，抓取结果的判断和下载计数全会出错；
  - 复位下载模块（清空下载区与内部计数）；
  - 显示「停止抓取」按钮；
  - `states.crawling = true`（账户被警告时，据此自动停止抓取）。
- 重置本轮结束标记 `userDone = false`。

### 4.2 用户级预检查

用 `filter.check({ userId })` 检查该用户是否被屏蔽（屏蔽名单 / mute），被屏蔽则跳过该用户、不发送任何请求。（屏蔽设定已在任务开始时预取。）

### 4.3 获取用户名

- `API.getUserProfile(id)` 获取用户名，用于在日志里显示。
- 请求失败（用户不存在、已注销或网络错误）→ 输出错误日志「获取用户资料失败，跳过该用户：{链接}」并跳过。
- 成功则输出（前两条为绿色）：开始抓取 {用户链接} 的作品，用户 ID 为 {ID}；他在队列中的位置是 {x/y}；开始获取作品列表。

### 4.4 获取作品 ID 列表

- `API.getUserWorksByType(id)` 获取该用户全部作品（插画 + 漫画 + 小说）的 ID 列表。（注意：请求出错时它返回空数组，与「没有作品」无法区分。）
- 按作品 ID 从大到小排序（从最新的作品开始）；如果设置的抓取数量小于总数，则裁剪。
- 覆写 `store.idList`，然后处理这个列表：
  1. 逐个对作品 ID 做 `filter.check`（作品级预检查），不符合的剔除，这样也不会发送请求；
  2. 剔除后列表为空 → 按「无结果」处理（见 4.6）；
  3. 数量大于 6000 → 输出提示使用小号下载的警告日志；输出「当前有 x 个作品」；
  4. **导出 ID 列表分支**：如果启用了「导出 ID 列表」，导出之后**这个用户就结束了**（返回，处理下一个用户）。⚠️ 这里不会触发 `stopCrawl`，否则会把整个抓取用户列表的任务停掉；
  5. 输出「开始获取作品信息」。

### 4.5 逐个抓取作品数据

串行（单线程）抓取每个作品的详细数据，**每两次请求之间**都加 `settings.slowCrawlDealy` 间隔（本模块总是慢速抓取，不判断 `states.slowCrawlMode`；每轮的第一个请求之前不需要）。唯一例外：下一个作品是小说、且缓存里已有数据时，不加间隔（不需要发请求）。

每个作品的处理（`InitPageBase.getWorksData` 的裁剪版）：

- **小说**：先尝试从缓存取数（`cacheWorkData.getWorkDataAsync`，避免与「自动合并系列小说」重复请求）；如果启用了自动合并且该小说属于系列，走合并流程（`autoMergeNovel.merge`）；如果它会被合并、且设置了合并时跳过，则它不进入抓取结果；否则保存到抓取结果。
- **插画 / 漫画**：`API.getArtworkData` 取数 + `saveArtworkData.save` 保存。
- 请求出错：状态码不正常 → 不重试，输出「因为网络错误跳过这个作品」的错误日志；请求本身失败（无状态码）→ 等 2 秒后重试同一个作品。
- 每处理完一个作品，输出进度行：➡️待处理 {x}, 共抓取到 {y} 个作品（持久行）。

### 4.6 一轮抓取结束

所有作品处理完后：

- **有抓取结果** → `crawlFinished`：记录完成时间；按设置排序结果；输出「共抓取到 n 个作品产生了 n 个抓取结果」+「✅抓取完毕」；触发 `crawlComplete`（下载模块据此启动下载）；按需自动导出结果（CSV / JSON）。
- **无抓取结果** → `noResult`：触发 `crawlComplete` + `crawlEmpty`；只输出日志（对应文案 `_抓取结果为零的提示`），不弹消息框——批量抓取时每个没结果的用户都弹框会连续堆叠。

### 4.7 等待本轮下载结束

- **有抓取结果时，本模块会等本轮下载结束，再处理下一个用户**（无结果的用户不需要等待）。
- 结束信号（任意一个）：`downloadComplete`（下载完成，被跳过的文件也算）、`downloadStop`（用户点了「放弃下载」）、`crawlEmpty`（没有抓取结果）。
- 用户点「放弃下载」时，还会输出一条提示（文案 `_抓取用户列表时放弃下载的提示`），说明放弃下载只会跳过当前用户、不会终止整个任务。该提示使用日志 key，连续放弃时只占一行。
- 等待方式：这些事件在模块里常驻监听（只置一个 `userDone` 标记），`waitUserDone()` 以 100ms 间隔轮询这个标记。不用「临时挂 promise」的方式，是因为 `crawlEmpty` 是**同步**触发的（就在抓取流程的调用栈里），等抓取结束再挂监听会漏掉它。
- 下载何时开始由「快速下载任务」的自动下载决定（`settings.autoStartDownloadForQuickDownload`）：
  - **开启**（默认）→ 下载自动开始，等 `downloadComplete` 后继续下一个用户；
  - **关闭** → 下载**就绪但不自动开始**（下载区域出现、进度停在 `0 / N`），**原地等待**，直到用户手动点「开始下载」或「放弃下载」才继续。
  - ⚠️ 这里不能跳过等待直接进入下一轮：下一轮的 `crawlStart` 会重置 store，把这一轮的结果和下载流程一起丢掉。

## 5. 任务结束

### 正常完成

所有用户处理完毕 → 先执行收尾（见下），再输出「✅抓取用户列表完毕」+ 绿色轻提示。

### 用户停止

「停止抓取」按钮在整个任务期间可见（包括下载阶段）。点击后：

- 先弹 `window.confirm` 确认（文案 `_停止抓取用户列表的提示`）。用户取消则什么都不发生、不会触发 `stopCrawl` 事件；确认只在点击按钮时出现，账户被警告触发的自动停止不会弹确认。
- 确认后：先执行收尾（见下），再输出「🛑已停止抓取用户列表」+ 红色轻提示。
- 中断检查：模块内用 `isInterrupted(epoch)`（`stopped` 或 `epoch !== runId`）在循环里和每个请求发出前检查；停止后不会再发送新的抓取请求（正在进行中的请求等它自然结束）。用 `runId` 还能防止「停止后立刻开始新任务」时，旧流程的残留异步代码在新任务里继续执行。
- 点击停止**不会中止当时正在进行的下载**：本模块只结束后续流程，当前下载会自然完成。
- 停止后**不能从中断处恢复**（收尾时已清除缓存数据）；「恢复」只发生在重新点击按钮时对缓存数据的那次询问。
- 与 `StopCrawl` 的协调（本模块激活时 `states.crawlUserList = true`）：
  - `crawlComplete` 时它不会隐藏按钮（下载阶段保持可见）；
  - 点停止时它跳过自己的「🛑已停止抓取」提示，避免与本模块的提示重复。

### 收尾（完成与停止共用）

- 还原 `window.onbeforeunload`（只还原自己设置的那个组合回调，不会覆盖别人的注册）；
- 清除 localStorage 里的任务数据；
- `states.crawlUserList = false`；
- **延后一个事件周期**（`setTimeout 0`）再复位 `states.quickCrawl`——如果立即复位，下载模块随后在事件队列里执行的 `readyDownload` 会把最后一轮结果当作「普通下载任务」处理并可能自动开始下载（取决于 `autoStartDownload`，默认 true），即使用户关闭了快速下载任务的自动下载；
- `states.busy = false`；隐藏「停止抓取」按钮。

## 6. 恢复任务

- 任务数据保存在 localStorage（键 `crawlUserListTask`）：用户 ID 列表、抓取数量、进度（正在处理哪个用户的索引）。全局唯一一份、不区分批次，新任务的数据覆盖旧数据。
- 不主动恢复：只有入口预检查里、用户对询问确认后才会恢复。
- 确认时如果下载器正忙（弹窗期间可能又忙了）→ 消息框提示「无法恢复…因为下载器正忙」，返回。
- 确认恢复后：输出任务开始日志 → 消息框「已恢复之前的任务…」→ 从 `progressIndex` 对应的那个用户开始重新处理（该用户之前的抓取/下载进度舍弃，重新抓取）。

## 7. 与其它模块的联动

| 联动点 | 行为 |
| --- | --- |
| 其它抓取任务 | 本任务进行中，`InitPageBase.crawlIdList` 里的守卫会拦截所有经 `crawlIdList` 事件发起的新抓取（首页的抓取作品列表 / 作品 ID 区间 / 导入作品 ID 列表、缩略图与作品页上的下载按钮、「抓取选择的作品」等），显示消息框「该操作已被阻止，原因是：…」。需要同时抓别的内容时，打开一个新的标签页。 |
| 账户被警告 | 抓取阶段 `states.crawling = true`（每轮 `crawlStart` 维护）→ 收到警告时自动触发 `stopCrawl` 停止本任务；下载阶段由 `downloadPause` 暂停下载。 |
| 断点续抓（Resume） | 每轮 `crawlStart` 会重置 store，与 Resume 互不冲突；恢复本任务时该用户重新抓取。 |
| 关闭页面提示 | `beforeunload` 用「包裹 + 还原」处理（`window.onbeforeunload` 只能有一个回调，全项目只有 `SelectWork` 也在用）。 |

# 已知问题

## 1. 排序的问题

如果一个用户同时有图片和小说作品，那么在最开始对作品排序时（按作品 ID 从大到小），并不能代表发布时间顺序。因为：
1. 此时只有 ID 数据，没有发表时间数据；
2. 小说的 ID 比图片作品小一个数量级，所以即使是新发表的小说，也经常会排在图片作品后面。
两者结合，导致只按 ID 排序会不准确。

该问题的影响：
- 只会影响同时有图片和小说作品的用户。
- 如果用户设置的抓取作品数量比较少，需要裁剪，就可能会导致只保留了图片作品（因为图片排在前面），小说一个都没保留（因为新发表的小说也会排在图片作品的后面）。
- 如果用户设置的抓取数量是全部（如 `-1`），则没有影响，因为此时不会发生裁剪。

## 2. 页面刷新后，恢复的下载任务不会被识别

这个问题的原因是：
- 页面刷新后，下载器会自动恢复未完成的下载任务；
- 但不会自动恢复“抓取用户列表”任务。

复现流程是这样的：
- 用户执行了“抓取用户列表”的任务。
- 在抓取完一个用户后，下载器会开始下载他的作品。
- 在下载途中刷新网页。
- 刷新网页之后，下载器会自动恢复未完成的下载任务。问题发生在这里，此时下载器并没有恢复“抓取用户列表”的状态，所以这次下载没有与“抓取用户列表”关联起来。所以当这次下载完成之后，“抓取用户列表”的进度不会增加。
- 如果之后用户恢复了未完成的“抓取用户列表”任务，下载器会从之前尚未处理完毕的用户开始执行，也就是前面说的“未完成的下载任务”所对应的用户。下载器会对这个用户重新抓取、下载一次。

这是功能设计导致的已知问题，不是 Bug：
未完成的“抓取用户列表”任务只能通过用户手动点击“抓取用户列表”按钮恢复。这是设计如此，因为如果打开首页就自动恢复的话，可能会干扰用户的操作。而且用户也可能确实不需要恢复之前未完成的“抓取用户列表”任务了，所以不自动恢复更稳妥。
