# 手动排除作品

日期：2026-09-24

本文档说明「手动排除作品」机制的工作方式，重点是：**被排除的作品在抓取流程和下载流程里分别是怎么被处理掉的**。

如果以后要重新理解这套机制，建议按这个顺序读代码：

1. `src/ts/ExcludeWork.ts` —— 用户操作的入口
2. `src/ts/WorkSelection.ts` —— 排除列表的保存与增删
3. `src/ts/filter/Filter.ts` 的 `checkExcluded()` —— 唯一的判断入口
4. `src/ts/store/Store.ts` 的 `removeWorkById()` / `removeWorkFromResult()`
5. `src/ts/download/DownloadControl.ts` 的 `handleExcludedWork()` / `removeExcludedWorks()`
6. `src/ts/crawlArtworkPage/SearchResultPreview.ts` 的 `onManuallyExcludeWork()` / `syncExcludedWorks()`
7. `src/ts/download/BookmarkAfterDL.ts` 的 `addBookmark()`

---

## 1. 这个功能是什么

用户在页面上触发「手动排除作品」（默认快捷键 <span class="blue">Alt</span> + <span class="blue">E</span>），把一个作品标记为「不想要」。之后：

- 还没被抓取的作品：**不会再进入抓取结果**
- 已经被抓取、还没下载的作品：**会被跳过下载**
- 无论下载有没有开始，它都会被**从抓取结果里移除**

参与这个功能的模块：

| 模块 | 职责 |
| --- | --- |
| `ExcludeWork` | 响应用户操作、给缩略图打「已排除」标记、触发「从抓取结果里移除」 |
| `WorkSelection` | 保存排除列表 `excludeIdList`，处理它和「手动选择作品」列表的互斥 |
| `Filter.checkExcluded()` | **唯一**的「这个作品被排除了吗」判断入口 |
| `Store` | 非下载阶段用 `removeWorkById()` 删除；下载结束整理时用 `removeWorkFromResult()` |
| `DownloadControl` | 下载阶段的两阶段处理 |
| `SearchResultPreview` | 搜索页预览列表的同步 |
| `BookmarkAfterDL` | 下载后收藏时再判断一次 |

⚠️ 它是 **toggle**：对同一个作品再按一次 <span class="blue">Alt</span> + <span class="blue">E</span> 是**取消排除**，不是「再排除一次」。

---

## 2. 两个关键数据结构

### 2.1 `workSelection.excludeIdList: IDData[]`

排除列表本身。每项是 `{ id: string, type: IDTypeString, title?: string }`。

- 加入 / 移除都是 **toggle**，由 `toggleExcludeId()` 负责
- 同时会把该作品从「手动选择作品」列表里移除（两个列表互斥）
- `type` 对于图像作品是**粗略的** `illusts`，不会区分 `manga`、`ugoira`

### 2.2 `states` 上的下载状态标记

判断「现在有没有下载任务在跑」需要两个标记：

| 标记 | 变 true | 变 false |
| --- | --- | --- |
| `downloading` | `downloadStart` | `downloadPause` / `downloadStop` / `downloadComplete` |
| `downloadPaused` | `downloadPause` | `downloadStart` / `downloadStop` / `downloadComplete` / `crawlStart` |

**暂停时 `downloading` 会变成 false**（它表示「正在传输」），但下载任务其实还在、之后可以继续。所以判断「有没有下载任务」**一律使用 `states.hasDownloadTask`**（getter，等于 `downloading || downloadPaused`），不要自己拼这两个标记 —— 这套判断散在多个模块里，条件写歪了就会出现「两个模块都处理」或「都不处理」。

---

## 3. 唯一的判断入口：`Filter.checkExcluded()`

```ts
/** 检查这个作品是否被用户手动排除。返回 true 表示保留，false 表示排除 */
public checkExcluded(id?, IDTypeString?): boolean
```

两点要注意：

1. **它只在 `Filter.check()` 收到 `option.id` 时才会被调用**（`Filter.check()` 做的第一件事就是它）。所以**下载路径里那些不带 `id` 的 `filter.check` 查不到排除** —— `Download.ts` 里检查宽高、体积、颜色的三处都不带 `id`，这就是「下载中排除不能靠过滤器生效」的原因。
2. 它处理了**类型宽松匹配**：列表里图像作品的类型是 `illusts`，而查询时可能传入更具体的 `manga`、`ugoira`、`unknown`，这些都会被 `illusts` 匹配上。

需要判断「某个作品是否被排除」时**复用它**，不要自己再写一套匹配逻辑。

---

## 4. 触发排除时发生什么

`ExcludeWork.addId(el, id, type)` 做三件事：

1. `workSelection.toggleExcludeId(id, type)` —— **一定会执行**，与下载状态无关
2. 如果是**新增**：
   - `addExcludedFlag()` 给缩略图打上「已排除」标记（立刻可见）
   - 然后 `if (!states.hasDownloadTask) { store.removeWorkById([id]) }`
3. 如果是**取消**：`removeExcludedFlag()` 只去掉标记

⚠️ 第 3 步**不会**把作品放回抓取结果。排除的「移除」效果是单向的，只有重新抓取（`filter.check` 不再拦它）才会让它回来。

## 5. 抓取阶段

### 5.1 还没抓到的作品：在四个检查点被挡住

排除列表是通过 `Filter.check()` 生效的，而抓取流程里有四个地方会调用它（都带 `id`）：

| 检查点 | 位置 | 效果 |
| --- | --- | --- |
| 过滤 id 列表 | `InitPageBase.getIdListFinished()` | 不合格的 id 根本不进入 `store.idList` |
| 获取作品数据前 | `InitPageBase.getWorksData()` | 拿到一条 id、在**发请求之前**再查一次，不合格就跳过 |
| 取下一个 id 前 | `InitPageBase.afterGetWorksData()` | 预检 `store.idList[0]`，不合格就 `shift()` 掉、**连请求都不发** |
| 各页面模块内部 | 例如 `InitSearchArtworkPage` 把作品推入 idList 之前 | 再加一道保险 |

后两个检查点是为了**省掉不必要的请求**，让抓取更快。所以排除一个还没抓到的作品，效果是**立刻生效**的。

⚠️ 已经发出去、正在返回的请求无法撤回；这些作品仍会走一遍「获取数据 → 检查」的流程，然后在检查点被丢掉。

### 5.2 已经抓到的作品：直接从抓取结果里删除

`store.removeWorkById([ids])` 会：

1. 从 `store.idList` 里按 id 找到并 `splice` 掉
2. 从 `store.resultMeta` 和 `store.result` 里过滤掉（前者每个作品一条，后者每个文件一条）
3. 从去重表 `artworkIDList` / `novelIDList` 里移除，避免以后 `addResult()` 因去重而拒绝重新加入
4. 如果真的删掉了东西，触发 `resultChange` 事件

**但它只在不存在下载任务时才会被调用**（见下一节）。

### 5.3 为什么抓取阶段可以放心删

`store.idList` 只用 `shift()` 和 `[0]` 消费，没有按下标遍历 —— 删掉一个非头部元素不影响消费顺序；删的若是头部，那个作品本来就被排除、跳过它正是期望行为。`store.result` / `store.resultMeta` 在抓取阶段只被读 `.length`，以及抓取结束时的 `.sort()`。

## 6. 下载阶段：两阶段处理

### 6.1 为什么不能直接删除

下载流程里有**三处数据结构靠同一组下标互相对应**：

- `store.result` —— 每个待下载的文件一条，下载按它的下标派发
- `downloadStates.states` —— 与 `store.result` 等长的状态数组（`-1` 未开始 / `0` 下载中 / `1` 完成）
- `DownloadControl.taskList[].index` —— 飞行中的任务记住自己的下标，完成时靠它写回状态

所以在下载中删 `store.result` 的元素会让另外两处的下标全部失效。

**另一个原因是不该发 `resultChange`。** `store.removeWorkById()` 会触发这个事件，而它有两处听众：

- `DownloadStates` 监听它时会重建 `states`（现在有拦截：**存在下载任务时不重建**，所以不会把进度清零）
- `DownloadControl` 自己也在监听它：下载进行中会因 `states.busy` 早退，但在下载「已完成 / 已停止 / 已暂停」之后就会走到 `readyDownload()` → **可能把整批重新下一次**（这条已用 `downloadCompleteOrStop || this.pause` 的早退挡住）

所以下载阶段采用两阶段方案，**两个阶段都刻意不触发 `resultChange`**：改用「直接改下载状态 + 刷新进度」的方式通知，不广播「结果集变了」这个信号。

### 6.2 阶段 1：`DownloadControl.handleExcludedWork()`

监听 `manuallyExcludeWork` 事件，在下载进行中（`states.hasDownloadTask`）处理：

1. 跳过 `novelSeries` —— 它的 id 是系列 id 而不是作品 id，在抓取结果里找不到对应记录（不在下载中时排除系列也是同样结果，行为一致）
2. 找出这个作品在 `store.result` 里占用的**文件下标**
3. 把这些文件里状态为 `-1`（**尚未开始**）的标记为 `1`（**已完成**）

   这里直接复用了「**跳过下载的文件也算正常下载**」这个既有约定，所以下载队列、进度分母、完成判定**都不需要改**

4. 状态为 `0`（正在下载）与 `1`（已完成）的**不动**：前者已在飞行中，后者文件已经在本地了
5. 从 `store.resultMeta` 里移除，让用户看到的抓取结果**立刻**更新
6. 把被跳过文件的 id 从 `errorIdList` 里剔除，否则 `checkCompleteWithError()` 的等式会提前成立，触发一次多余的「暂停 + 重试」
7. 记入 `excludedWorkIdList`，然后 `setDownloaded()` 刷新进度与完成判定
   （暂停中则跳过这一步：`setDownloaded()` 会在全部完成时 `reset()`，把「已暂停」状态清掉）

### 6.3 阶段 2：`DownloadControl.removeExcludedWorks()`

监听 `downloadComplete` 与 `downloadStop`，这时**已经没有在飞的文件**，可以安全地改下标：

1. 对 `excludedWorkIdList` 里的每个 id 调 `Store.removeWorkFromResult(idNum)` ——
   它删 `result` 和 `resultMeta`，但**不改 `idList`、不触发 `resultChange`**，并返回被删文件在 `result` 里的原下标
2. 用这些下标调 `DownloadStates.removeItems()` —— 从后往前 `splice`，让 `states` 与 `result` 保持等长
3. 刷新 `store.remainingDownload`

⚠️ 阶段 2 **不能**把 `downloadPause` 也算作触发时机：暂停时可能仍有在飞任务，删 `states` 会让它们的下标错位。

## 7. 其他会受影响的地方

### 7.1 搜索页的预览列表（`SearchResultPreview`）

搜索页的预览列表用的是模块**自己的快照** `this.resultMeta`，所以需要单独同步。

**`onManuallyExcludeWork()`** 有三个早退：

| 条件 | 交给谁处理 |
| --- | --- |
| `states.hasDownloadTask` | `DownloadControl` 的两阶段 |
| 不是图像作品（`novels` / `novelSeries`） | 预览列表里只有图像作品，不处理 |
| `this.resultMeta` 为空（= 抓取尚未结束） | `ExcludeWork` 已经处理过了 |

只有三个条件都不成立时，才改快照、`reAddResult()`、重绘、发 `resultChange`。
⚠️ 之所以要在下载中早退，是因为这里的 `reAddResult()` 会 `store.reset()` 并**重建 `store.result`** —— 那比多发一个事件严重得多。

**抓取中**排除的作品，`store.resultMeta` 里已经没有了，但页面上的卡片要等抓取完成（`finishCrawl` 会清空并重绘）才消失。这是显示上的延迟，数据是正确的。

**下载结束后**由 `syncExcludedWorks()` 收尾：以 `store.resultMeta` 为准求交集，把快照收窄，再 `showCount()` + `renderCurrentPage()`。延后一拍执行，这样不必依赖「`DownloadControl` 的监听先注册」这个隐式顺序。

### 7.2 下载后收藏（`BookmarkAfterDL`）

`addBookmark()` 在**真正调用 `bookmark.add()` 之前**用 `filter.checkExcluded()` 判断：命中就

- 输出警告日志（带作品链接）
- `successCount++` —— **视为收藏完成**，否则进度会一直差几个、永远等不到「收藏完毕」
- `continue`，不发起收藏请求

因为收藏队列是串行 + 每 200ms 一个的，放在这个位置判断，**排队期间才被排除的作品也会被跳过**。

## 8. 生效范围速查

| 场景 | `removeWorkById` 是否执行 | 已经抓到的作品 | 尚未下载的作品 |
| --- | --- | --- | --- |
| 抓取中（任意页面） | ✅ 执行 | ✅ 立刻移除 | ✅ 被 `filter.check` 挡住 |
| 下载中 | ❌ 跳过，交给两阶段 | ✅ 立刻从 `resultMeta` 移除 | ✅ 未开始的文件被标记为「已跳过」；下载结束后从 `result` 里删净 |
| 下载暂停 | ❌ 跳过，同样交给两阶段 | ✅ 立刻从 `resultMeta` 移除 | ✅ 未开始的文件被标记为「已跳过」；**进度不会被重置** |
| 空闲（无任务） | ✅ 执行 | ✅ 移除 | — |
| 书签模式中 | ✅ 执行 | ✅ 移除 | — |
| 合并系列小说 | — | — | ✅ 跳过（`MergeNovel` 的 `filter.check` 带 `id`） |
| 下载后收藏 | — | ✅ 跳过收藏并计入完成 | — |

## 9. 已知限制

- **是 toggle**：再按一次是取消排除，而取消**不会**把作品放回抓取结果。
- **排除系列小说（`novelSeries`）是 no-op**：系列 id 不是作品 id，在抓取结果里找不到对应记录；它里面的单篇小说不会被连带排除。
- **正在下载中的文件不会被中断**，它会照常下载完；被跳过的只是「尚未开始」的文件。
- **下载中排除后如果不继续也不停止下载**：`store.result` 里会留着已标记为「已跳过」的项。它不会被下载，下次抓取时 `store.reset()` 会清掉。
- **抓取阶段排除会让 `idListLength` 不再准确**（它在 id 列表过滤完时记录一次），因此 `mergedNovelCount === idListLength` 这个判断可能**漏报一次**「所有作品都被合并为系列小说」的提示。只影响一条日志。
- **抓取中的排除不会更新搜索页已显示的卡片**，要等抓取完成重绘。搜索页以外的页面不显示预览卡片，没有这个问题。

---

## 10. 一句话总结

抓取阶段靠 **`filter.check` 拦截 + `removeWorkById` 删除**，下载阶段靠 **「标记为已跳过 + 结束后整理」的两阶段方案**；两条路径的分界线是 `states.hasDownloadTask`，而全部判断最终都收束到 `Filter.checkExcluded()` 这一个入口。
