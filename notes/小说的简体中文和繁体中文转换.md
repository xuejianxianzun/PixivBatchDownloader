# 小说的简体中文和繁体中文转换

日期：2026-10-05

## 转换选项

用户可以在“简繁转换”设置里选择：

- 不转换（默认）
- 简体转繁体
- 繁体转简体

这个设置**没有开关**，直接由这 3 个单选按钮组成。

> 设置项的编号是 110。

## 转换范围

### 会转换的内容

- 只会对 MakeSingleNovelFile 和 MergeNovel 模块生成的小说文件进行转换。
- 对 TXT 和 EPUB 格式都生效
- 对单篇小说和系列小说都生效
- 会转换小说和系列小说的标题、简介、正文，以及系列的“设定资料”（Glossary）。

  具体的字段：

  | 位置 | 会转换的字段 |
  | --- | --- |
  | 单篇小说 TXT | 标题、简介、正文 |
  | 单篇小说 EPUB | 书名（`<dc:title>`）、书籍简介（`<dc:description>`）、章节名、元数据页里的标题与简介、正文 |
  | 系列 TXT | 系列标题、系列简介、章节列表里的标题、每章的标题与简介、正文、设定资料 |
  | 系列 EPUB | 系列标题（书名）、系列简介、章节列表里的标题、每章的标题与简介、章节名、正文、设定资料 |

  > 设定资料里可能会含有图片标记 `[glossaryImage-xxx]`。这些标记是纯 ASCII，转换时不会被改动。

### 只对中文内容生效，并且区分简体与繁体

转换**只对语言标签是中文的内容生效**，日语、韩语、英语等其他语言一律跳过。
而且必须区分简体与繁体：**原文已经是目标用字时不会转换**。

原因是 opencc 的字典是为中文准备的，对日语执行转换会把日语汉字改成中文写法：

| 日语原文 | 经过“简体转繁体” | 经过“繁体转简体” |
| --- | --- | --- |
| 図書館 | 圖書館 ❌ | 図书馆 ❌ |
| 手紙 | 手紙 | 手纸 ❌ |
| 公園 | 公園 | 公园 ❌ |
| 携帯電話 | 攜帶電話 ❌ | 携帯电话 ❌ |
| 画面 | 畫面 ❌ | 画面 |

pixiv 上的小说绝大多数是日语，所以这个判断不能省略。

判断依据是**内容原本的语言标签**（单篇小说用 `NovelMeta.language`，
系列里的每一篇用各自 `NovelSummary.language`；系列本身的系列标题、简介、设定资料
没有语言标签，所以使用系列里第一篇小说的语言）：

| 语言标签 | 简体转繁体 | 繁体转简体 |
| --- | --- | --- |
| `zh-cn`、`zh-Hans`、`zh-sg`、`zh-my`（简体） | 转换 | **跳过** |
| `zh-tw`、`zh-hk`、`zh-mo`、`zh-Hant`（繁体） | **跳过** | 转换 |
| `zh`、`zh-yue`（是中文但无法判断字形） | **跳过** | **跳过** |
| `ja`、`ko`、`en` 等非中文 | **跳过** | **跳过** |
| 空 / 取不到 | **跳过** | **跳过** |

⚠️ 无法判断时一律跳过：语言标签为空、或者是 `zh` 这样没有次标签的标签时，
并不知道它是不是中文，而把非中文内容丢进 opencc 会破坏文本，所以宁可不转换。

⚠️ 为什么“原文已经是目标用字”也要跳过：这种转换没有意义，还有副作用。
繁体转简体必须从 `twp` 输入，而 `twp` 会转换台湾常用词，
把已经是简体的内容再过一遍没有任何收益，反而可能改动地区用词
（例如把「軟體」「資訊」转成不存在的「软体」「资讯」）。

判断字形的逻辑统一放在 `src/ts/utils/ChineseLang.ts` 的 `getScript()`
（`notChinese` / `simplified` / `traditional` / `unknown`），
`ConvertNovelText.needConvert()` 和 `EPUBSetting.applyNovelTextConvert()` 都用它，
以保证「是否转换」与「语言标签是否被修正」永远一致。

### 不会转换的内容

- 文件名里的小说标题不会转换。实际上转换设置完全不会影响文件名。
- 对于在小说文件里保存的元数据（对应的设置是 `saveNovelMeta`），不会转换作者名字、标签列表、链接。因为这是专有名词，需要保持原样。如果转换的话，作者名字或标签名字与原本的不一样，在 pixiv 上搜索对应内容的话，就搜不到了。
- 对于在单独的文件里保存的元数据（`SaveWorkMeta`，对小说是否生效由 `saveMetaType3` 决定），不会转换。虽然它里面包含标题和简介，但不会转换。
- 对于在单独的 TXT 文件里保存的简介（`SaveWorkDescription`，对应的总开关是 `saveWorkDescription`，
  对小说是否生效由 `saveDescriptionType3` 决定），不会转换单独保存的简介。

## 附带影响

### 影响 EPUB 的语言标签

当需要转换时，下载器除了会转换小说内容，还会修改 EPUB 文件的语言标记。

例如：

小说原本的语言是简体，而且用户启用了简转繁，那么下载器会把 EPUB 文件的语言代码设置为转换后的 `zh-tw`。反之亦然。

⚠️ 需要注意两点：

1. **被修正的是“EPUB 文件实际使用的语言标签”**，也就是“EPUB 文件的语言标签”这个设置最终决定的
   那个值，不一定是小说原本的语言。例如把语言来源设成了“使用下载器的语言”或“自定义”，
   也会对这个来源的结果应用同样的修正。
2. 系列小说的语言标签不是取自系列数据 —— 系列数据里的 `language` **总是 `ja`**，
   所以下载器会去取系列里第一篇小说的语言来用。

修正规则（**只在正文确实会被转换时生效**，其他情况一律原样返回）：

| 转换设置 | 原本的语言标签 | 写入 EPUB 的语言标签 |
| --- | --- | --- |
| 简体转繁体 | `zh-cn`、`zh-Hans`、`zh-sg`、`zh-my` | `zh-tw` |
| 简体转繁体 | `zh-tw`、`zh-hk`、`zh-mo`、`zh-Hant` | 不变（已经是繁体） |
| 繁体转简体 | `zh-tw`、`zh-hk`、`zh-mo`、`zh-Hant` | `zh-cn` |
| 繁体转简体 | `zh-cn`、`zh-Hans`、`zh-sg`、`zh-my` | 不变（已经是简体） |
| 任意 | `zh`、`zh-yue`、空值、非中文 | 不变（正文不会转换） |

### 影响 EPUB 的排版方向

如果因为转换小说语言而修改了 EPUB 的语言标签，那么**有可能**会影响之后的“EPUB 文件的排版方向”的处理。之所以说“有可能”，是因为这要看排版方向里的设置：
只有当用户启用了“对这些语言的小说使用竖排”，并且转换前后的语言的排版方向不一致时，才会有影响。

例如：

原本小说的语言是 `zh-cn`，并且排版设置里是横排。转换为 `zh-tw` 后，如果用户在排版设置里设置了 `zh-tw` 为竖排，那么转换后的内容就会使用竖排。

这是因为语言标签的修正发生在 `EPUBSetting.resolve()` **内部**，位于计算排版方向之前，
所以排版方向始终是基于**修正后的语言标签**来判断的。

## 技术方案

### 1. 库的选择：opencc-js

使用 [opencc-js](https://github.com/nk2028/opencc-js)，版本 **`1.5.0-beta.0`**。

选它的理由：它是 OpenCC 的纯 JS 移植，词典齐全，而且在浏览器里可以直接使用。

#### 用 `twp` 而不是 `tw`

opencc-js 的 locale 里，`tw` 只做字形层面的繁体转换，`twp` 还会额外转换**台湾常用词**。
这里两个方向都使用 `twp`。

**反向（繁→简）必须用 `twp`**，否则会产出错误甚至不存在的简体词：

| 台湾繁体 | 用 `tw2s`（错） | 用 `tw2sp`（对） |
| --- | --- | --- |
| 軟體 | 软体 | 软件 |
| 記憶體 | 记忆体 | 内存 |
| 資訊 | 资讯 | 信息 |
| 印表機 | 印表机 | 打印机 |
| 網路 | 网路 | 网络 |
| 部落格 | 部落格 | 博客 |

**正向（简→繁）`twp` 更地道**：软件→軟體、信息→資訊、鼠标点击→滑鼠點選、自行车→腳踏車、
博客→部落格、窗口→視窗；而且“视频通话”是**整条词组命中**变成“視訊通話”，不会变成别扭的“影片通話”。

已知的小瑕疵（来自上游词典，不影响整体选择）：

- “信息”一律转成“資訊”（“一条信息”这种语境下略怪）
- 句子里的“硬盘”没能转成“硬碟”（单独测词能转，分词之后词组未命中）

#### 体积与 Tree Shaking

opencc-js 完整的 ESM 文件约 1.13 MB。**Tree Shaking 对这里几乎没用**：

`dict/STPhrases.js` 就占了 **982 KB**（gzip 407 KB），它是“简→繁”用的分词消歧字典
（“头发/头髮” vs “出发/出發”、“干/乾/幹”全靠它），绕不开。

| 文件 | 未压缩 | gzip |
| --- | --- | --- |
| `full.js`（所有方向） | 1165 KB | 499 KB |
| `cn2t.js`（简→繁的全部方向） | 1075 KB | 456 KB |
| `t2cn.js`（繁→简的全部方向） | 104 KB | 52 KB |

⇒ 简转繁的体积下限就是 ~1.05 MB，树摇最多再省 8%。

因此采用的策略是**按方向拆分 + 按需加载**：直接使用官方切好的 UMD 产物 `cn2t.js` / `t2cn.js`，
只在用户真的启用了某个方向时才加载它。这样：

- 不启用转换：0 开销
- 只启用繁转简：104 KB
- 只启用简转繁：1075 KB（这个省不掉）

> ⚠️ UMD 版两个文件暴露的全局变量**都叫 `OpenCC`**，同时加载会互相覆盖。
> 本项目一次只会加载其中一个，不存在这个问题。

### 2. 加载方式

项目原本的惯例是把第三方库放在 `src/static/lib/` 里，然后在 manifest 的 `content_scripts` 里静态列出
（jepub、jszip 等都是这样）。opencc 不能照搬 —— 那会导致**每个 pixiv 页面都要下载并解析 1 MB 的字典**。

现在的做法完全沿用了 `ConvertUgoira/ToAPNG.ts` 加载 pako / UPNG 的现成套路：

```ts
const [libRes, workerRes] = await Promise.all([
  fetch(browser.runtime.getURL(config.file)),
  fetch(browser.runtime.getURL(workerFile)),
])
// 把 opencc 的 UMD 文件和 worker 脚本拼成一个 blob
const url = URL.createObjectURL(
  new Blob([libText, '\n', workerText], { type: 'application/javascript' })
)
const worker = new Worker(url)
```

三个文件都加进了 manifest 的 `web_accessible_resources`：

| 文件 | 大小 |
| --- | --- |
| `lib/opencc-cn2t.js` | 1075 KB |
| `lib/opencc-t2cn.js` | 104 KB |
| `lib/opencc.worker.js` | 1 KB（自写） |

为什么这样写：

- **不用 ESM 的 `import()`**：Firefox 的扩展里动态 import 有限制，用 fetch + Blob 更稳。
- **不用 `eval`**：MV3 的 CSP 禁止。
- **放在 Worker 里转换**：避免长文本转换阻塞页面主线程。

`opencc.worker.js` 是配套的胶水脚本，它被**拼接在 UMD 文件之后**，所以可以直接使用 `OpenCC` 全局变量。
它做两件事：把 `{ from, to }` 转成 opencc 的 `Converter` 配置；**缓存 converter**
（构建字典的 trie 有开销，同一个方向只构建一次）。

### 3. 模块结构

`src/ts/download/ConvertNovelText.ts`：

| 成员 | 作用 |
| --- | --- |
| 构造函数 | 监听 `EVT.list.settingChange`，当变化的设置是 `convertNovelText` 时立即加载对应的字典；切到“不转换”则销毁 worker 释放内存 |
| `needConvert(language)` | 判断某个语言标签是否需要转换。非中文（日语等）跳过，原文已经是目标用字的中文跳过，无法判断字形时也跳过 |
| `logStart(idData, language)` | 输出日志：`转换这篇小说的语言（{转换方向}）：{作品链接}`。链接由 `Tools.createWorkLinkByIDData` 生成。不需要转换时不输出 |
| `convert(content, language)` | 转换文本。不需要转换时直接返回原文；失败时记 `log.error` 并**返回原文**，绝不中断下载 |

配套的 langText：`_简繁转换`、`_不转换`、`_简体转繁体`、`_繁体转简体`、
`_转换这篇小说的语言`、`_转换小说的语言失败`。

### 4. 接入点

正文的 4 个接入点：

| 模块 | 方法 |
| --- | --- |
| `MakeSingleNovelFile` | `makeTXT`、`makeEPUB` |
| `MergeNovel` | `buildTXTNovelSection`、`buildEPUBChapterContent` |

日志的输出时机：

- 单篇小说：每次转换前输出一条（传 `{ id, type: 'novels', title }`）
- 系列小说：**整个系列只输出一条**，在 `mergeByFormat()` 开头（传 `{ id, type: 'novelSeries', title }`），
  不会每章刷屏

元数据的转换做了去重处理，避免同一个文本被重复转换：

- `MakeSingleNovelFile.makeMeta(data, title, description)` 改成接收**已经转换好的**标题和简介。
  `makeTXT` 只在需要保存元数据时才转换；`makeEPUB` 总是转换（因为书名、简介、章节名都用得到）。
- `MergeNovel` 增加了 `metaSeriesTitle` / `metaSeriesCaption` / `metaSeriesGlossary` /
  `metaNovelText: Map<小说 id, { title, description }>`，
  在 `mergeByFormat()` 开头由 `convertMetaText()` **一次性转换**（否则“章节列表”和“章节标题”
  会把同一个标题各转一遍），之后统一走 `metaNovelTitle(data)` / `metaNovelDescription(data)` 取值。

⚠️ 这里**没有直接改写 `this.seriesTitle`**：它还用于下载记录和日志里的链接文本，
改了会和 pixiv 的原始数据不一致。设定资料同理，另存为 `metaSeriesGlossary`
（`seriesGlossaryText` 还要留给图片标记替换等环节使用）。

语言标签的来源（用于判断是否需要转换）：

- 单篇小说：`data.language`（`NovelMeta`）
- 系列里的每一篇：`NovelSummary` 上**新加的 `language` 字段**，在 `createNovelSummary()` 里从
  `data.body.language` 取（原本 `NovelSummary` 里没有这个字段）
- 系列的系列标题 / 简介 / 设定资料：系列数据本身没有可靠语言（`language` 恒为 `ja`），
  所以用 `allNovelData[0].language`，也就是第一篇小说的语言

### 5. EPUB 的语言标签与排版方向

字形判断（简体 / 繁体）统一由 `src/ts/utils/ChineseLang.ts` 的 `getScript()` 提供，
`needConvert()` 与 `applyNovelTextConvert()` 共用，避免两边规则不一致。

`src/ts/download/EPUBSetting.ts` 里新增 `applyNovelTextConvert(langCode)`，
并在 `resolve()` **内部**调用：

```
getLangCode()  →  applyNovelTextConvert()  →  getWritingMode()
```

放在 `resolve()` 内部而不是在各个调用点之后，有两个原因：

1. 让排版方向基于**修正后的**语言标签计算（语言列表里写了 `zh-tw` 时，转成繁体后就该变竖排）
2. 以后新增调用点不会漏掉这一步 —— 只调用 `resolve()` 就自动生效

### 6. 性能

在 node 里用 `vm` 模拟 worker 环境实测：

| 项目 | 耗时 |
| --- | --- |
| 加载并解析字典 | 4 ms |
| 154 KB 文本首次转换（含构建 trie） | 182 ms |
| 同样的文本再次转换（已缓存） | 23 ms |

小说正文通常在几百 KB 以内，所以实际感受不到延迟。

### 7. 已知限制

- 单独保存的元数据文件（`SaveWorkMeta`）里的 Title / Description **没有转换**，
  和小说文件内部的处理不一致。处理方式：目前不处理（不转换）。
- `twp` 词典自身的瑕疵（见上），来自上游 opencc-js。
- 只处理简体中文 ↔ 繁体中文，不涉及其他语言的转换。
