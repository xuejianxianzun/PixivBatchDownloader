# 添加自定义快捷键功能

## 概述

现在下载器有很多快捷键。有些用户想修改快捷键（特别是当一些快捷键与其他扩展有冲突时），所以需要添加自定义快捷键的功能。

下载器的快捷键分为一级快捷键和二级快捷键。一级快捷键是在 pixiv 的网页里始终生效的，可以直接使用（不过有些只在特定页面里生效）；二级快捷键则是某些功能的子快捷键。例如：
- Alt + X 是一级快捷键，它用来切换显示下载器的设置面板，在任何时候都可以使用
- 在预览作品时，可以使用二级快捷键（例如复制作品信息的 `Alt + C`）。二级快捷键仅在对应功能界面显示时工作；如果该界面未显示，它就不会生效。

## 一级快捷键列表

现在有 9 个一级快捷键：

| 快捷键  | 作用                           | 使用该快捷键的模块                          | 生效的页面       |
| ------- | ------------------------------ | ------------------------------------------- | ---------------- |
| Alt + X | 查看/关闭设置面板              | src\ts\setting\SettingsPanelShell.ts        | 所有页面         |
| Alt + Z | 点击默认的抓取按钮             | src\ts\setting\SettingsPanelShell.ts        | 所有页面         |
| L       | 查看/关闭日志区域              | src\ts\ShowLogButton.ts                     | 所有页面         |
| Alt + S | 手动选择作品                   | src\ts\SelectWork.ts                        | 所有页面         |
| Alt + E | 手动排除作品                   | src\ts\ExcludeWork.ts                       | 所有页面         |
| Alt + P | 启用/关闭预览作品功能          | src\ts\PreviewWork.ts                       | 所有页面         |
| Alt + Q | 在作品页面里，快速下载当前作品 | src\ts\crawlMixedPage\QuickCrawl.ts         | 仅在作品页面生效 |

## 需求

- 保持现在在内容脚本里监听 keydown 事件的方式来监听快捷键。事件绑定在捕获阶段，以便在必要时阻止默认事件。排除在输入控件里的按键，因为此时用户在输入文本。
- 只需要让用户设置一级快捷键，不需要让用户设置二级快捷键。
- 如果用户修改了这些快捷键，那么下载器在绑定时需要使用用户设置的快捷键。
- 能兼容不同操作系统的按键（主要是 MacOS 的 `⌘`）。
- 需要考虑到这是在浏览器的网页里使用 JS 来处理快捷键设置，如果有些功能难以实现，或者有些组合键无法在这个环境里由用户设置，可以提出来，进行简化处理。
- 需要在设置面板里添加一个设置，并添加一个对应的模块让用户可以查看和修改快捷键。这个设置项的编号 `no` 是 `107`, 添加到编号 `97` 之后。这个设置项和模块的内容先不用详细考虑，因为在确定具体方案之前，它们的内容也无法完全确定。

允许用户使用这些按键作为快捷键：
- 数字 0 - 9
- 字母 A - Z
- Ctrl
- Alt
- Shift
- metaKey（MacOS 的 `⌘`）

其中，数字和字母可以单独使用，例如下载器已经使用了快捷键 `L` 来查看/隐藏日志区域。修饰按键（Ctrl、Alt、Shift，以及 Mac 的 `⌘`/meta）可以任意组合使用（即允许 Ctrl + Alt + A 这样，也允许 `⌘` + A），但不允许只使用修饰键，它们必须配合数字或字母一起使用。

其实之前该程序已经实现了另一套自定义快捷键的功能：在 manifest 里声明默认快捷键，由浏览器管理。现在我已经取消了这些代码，不过我保留了之前一些文件里的修改痕迹，主要是借鉴把命令作为 JS 事件进行派发的机制。在 `src/ts/EVT.ts` 里声明了 9 个快捷键命令，其他模块通过监听自己需要的使用的快捷键如 `window.addEventListener(EVT.list.commandToggleSelectWork` 来执行动作。其中只有 `commandToggleLogsArea` 命令目前尚未被使用（因为在之前修改时单个 `L` 无法作为浏览器快捷键）。

如果要延续这个机制，需要添加一个模块来专门监听快捷键和派发命令。

## 可行性分析

> 分析基于 2026-08-25 仓库实际代码状态。结论先行：**可行，且推荐采用“在内容脚本里集中监听 keydown 并派发 EVT 命令事件”的方案（下文方案 B）**。该方案不仅满足需求，还能顺带修复当前一个隐患。

### 一、当前代码现状（重要前提）

下载器已经存在一套“命令作为 JS 事件派发”的机制，只是目前处于**只接好监听端、缺少派发端**的半成品状态：

1. `src/ts/EVT.ts` 里已声明 9 个快捷键命令事件：`commandToggleLogsArea`、`commandToggleSettingsPanel`、`commandStartDefaultCrawl`、`commandToggleSelectWork`、`commandToggleExcludeWork`、`commandTogglePreviewWork`、`commandQuickDownload`、`commandQuickBookmark`、`commandCopyWorkInfo`。
2. 9 个一级快捷键对应的动作模块**都已改为监听这些 EVT 命令事件**（不再各自监听 keydown）：
   - `SettingsPanelShell.ts:210,214`（Alt+X / Alt+Z）
   - `SelectWork.ts:131`（Alt+S）
   - `ExcludeWork.ts:119`（Alt+E；该文件注释曾写 `Alt+W`，原因是此前用浏览器 `commands` API 时不允许把 `Alt+E` 设为默认键而临时改的，现采用方案 B 不受该限制，已改回 `Alt+E`）
   - `PreviewWork.ts:364,374`（Alt+P / Alt+C）
   - `crawlMixedPage/QuickCrawl.ts:46`（Alt+Q）
   - `pageFunciton/QuickBookmark.ts:35`（Alt+B）
   - `pageFunciton/CopyButtonOnWorkPage.ts:56`、`ImageViewer.ts:185`、`ShowOriginSizeImage.ts:273`（`commandCopyWorkInfo`，即 Alt+C）
3. **但是没有任何代码去派发这些命令事件**：
   - 仓库内不存在 `CommandReceiver` 模块（`Glob` 未找到）；
   - `manifest.json` 里没有 `commands` 字段；
   - `background.ts` 没有 `browser.commands.onCommand` 监听；
   - 全仓库搜索 `EVT.fire(...command...)` 也没有任何地方触发这些命令事件。
4. 唯一的例外是 `ShowLogButton.ts`：它**保留了自己的 keydown 监听**（`bindKeydown()`，`ev.code === 'KeyL'`），因此 `L` 这个一级快捷键目前仍可正常使用；而 `EVT.list.commandToggleLogsArea` 声明了却从未被使用。

**由此得出一个关键结论**：在当前的代码状态下，8 个 `Alt+*` 一级快捷键（Alt+X/Z/S/E/P/Q/B/C）其实是**失效的**——动作模块在等命令，但没有任何东西去触发命令。本功能要新增的“派发模块”正好能把这 8 个快捷键一并修复。这也验证了文档开头“之前做了另一套……我已取消这些代码，保留修改痕迹”的描述：`commands` API 方案被废弃（见 `notes/在扩展管理里允许用户修改快捷键-已废弃.md`），但监听端的改造残留了下来。

### 二、方案对比

#### 方案 A：纯浏览器 `commands` API（即已废弃的方案）——不推荐

要点（来自已废弃文档与 MDN 限制）：

- **单键不被允许**：`commands` 要求至少带一个修饰键（Ctrl/Alt/Command/Shift），只有特殊的 `_execute_*` 命令可例外。这与需求“字母可单独使用（如 L）”直接冲突——这也正是为什么 `L` 当时被排除在该机制之外。
- **运行时自定义能力极弱**：Firefox 完全不支持 `commands.update`；Chrome 的 `commands.update` 也限制重重（只能改带 suggested key 的命令，且需通过 `chrome.commands` 专用流程）。无法做到“用户在设置面板里自由把 Alt+X 改成 Ctrl+K”这种体验。
- **默认快捷键数量受限**：Chrome 限制扩展最多预设 4 个默认快捷键，无法一次性预设 9 个。
- **跨平台差异**：`commands` 在 manifest 里用 `default` 和 `mac` 两个字段分别表达 Win/Linux 与 Mac 的组合，浏览器负责把 ⌘ 映射好，这点对 Mac 友好；但上述三条限制已经让整体方案不成立。
- **输入框内仍会触发**：浏览器命令即便焦点在输入框也会生效，无法像 keydown 方案那样主动排除输入场景，反而更难处理。

**结论**：无法满足“用户可自定义 + 允许单键 L + 全平台一致”这一核心需求，故之前被废弃，本次也不应采用。

#### 方案 B：内容脚本集中监听 keydown，派发 EVT 命令事件——推荐

- 复用已经接好的 9 个 EVT 命令监听端，只**新增一个集中派发模块 `HotkeyListener`**（放在**内容脚本**里，而非 background——原后台脚本 `CommandReceiver.ts` 已被删除，因此新模块不再沿用该命名）。
- 该模块：`addEventListener('keydown', handler, true)`（捕获阶段）→ 读取设置里用户自定义的快捷键映射 → 匹配到则 `EVT.fire('commandXxx')` → 各动作模块早已就位的监听者执行对应动作。
- **优点**：
  1. 直接满足需求全部条目：保留当前 keydown 捕获方式、仅一级可改、用户可改、支持单键 `L` 与修饰键任意组合、跨浏览器一致。
  2. 顺带修复当前 8 个 `Alt+*` 快捷键失效的回归问题（监听端已就绪，补上派发端即恢复）。
  3. 不依赖浏览器 `commands` API，规避其平台差异与数量限制。
  4. 改动面小：9 个动作模块的监听端已接好，无需改动；只需新增派发模块 + 设置项 + 编辑 UI。
- **需要新增**：
  - 集中派发模块：`src/ts/HotkeyListener.ts`（前台内容脚本，负责监听 keydown 并派发 EVT 命令；原后台 `CommandReceiver.ts` 已删除）；
  - 设置项（编号 `no=107`，放在 `97` 之后）；
  - 一个让用户查看/修改快捷键的编辑 UI 模块。
- **可行性：高。**

### 三、MacOS ⌘ 的处理建议（需求里的疑问）

在 DOM 的 `keydown` 事件里，Mac 的 ⌘（Command）对应 `ev.metaKey`，**不是** `ev.ctrlKey`。派发模块直接判断 `ev.metaKey` 即可，技术上没有难点。具体给出两种可选口径：

- **保守口径（严格按需求）**：需求“允许的修饰键”只列了 Ctrl/Alt/Shift，未列 ⌘。那么 Mac 上直接用 `Alt+X`（即 Option+X）、`Ctrl+X`（Control+X）即可，`keydown` 都能正确上报 `altKey`/`ctrlKey`，无需为 ⌘ 做任何特殊处理，默认值保持与 Win/Linux 一致。
- **确定口径（已采纳）**：把 ⌘（meta）作为**可选修饰键**开放给所有用户（Mac 用户主要使用 ⌘）。做法：
  - 编辑 UI 按平台显示修饰键标签：Mac 显示 `⌘ / ⌥ / ⌃ / ⇧`，Win/Linux 显示 `Ctrl / Alt / Shift`。
  - 存储结构统一为 `{ key: 'KeyX', ctrl, alt, shift, meta }` 四个布尔标志（加一个主键），派发时按 `ev.ctrlKey / altKey / shiftKey / metaKey` 比对。
  - 这样 Mac 用户可以把快捷键设成 `⌘+X`，与他们的使用习惯一致。

**按键识别的统一约定**：一律使用 `ev.code`（如 `'KeyX'`、`'Digit1'`）来识别主键，不要使用 `ev.key` 或 locale 相关字符串，以免受输入法、键盘布局（如 AZERTY）影响。

**关于 ⌘ 的冲突提示**：`⌘+W/T/R` 等被浏览器吞掉、不会到达页面 keydown；编辑 UI 应对这类保留组合做黑名单校验并提示用户，避免“设了却不触发”。

### 四、浏览器网页环境里的限制（需求要求列出）

1. **浏览器/OS 保留组合不会到达页面 keydown**：如 `Ctrl+T/W/N/R`、`Ctrl+Shift+J`、部分 `F1–F12`、`Ctrl+数字` 切标签等。用户即便选了也不会触发，必须在编辑 UI 里校验并提示，而不是静默接受。
2. **输入场景应排除**：在 `INPUT` / `TEXTAREA` / `contentEditable` 里按键不应触发快捷键（否则用户正在打字也会触发动作）。`ShowLogButton.ts` 已有此判断逻辑，可直接复用。`L` 迁移到集中派发后也应沿用该排除逻辑。
3. **焦点在浏览器自身 UI（地址栏、DevTools）时不触发**：内容脚本收不到这类按键，对本扩展场景是可接受的。
4. **单键只有 keydown 方案支持**：`commands` API 不支持单键，再次说明方案 B 的必要性。
5. **跨浏览器一致**：Chrome / Firefox / Edge 的内容脚本 `keydown` 行为一致，无需后台转发，方案 B 天然跨平台。
6. **页面与其它扩展的按键占用**：Pixiv 自身或用户安装的其他扩展可能占用某些组合——这正是“自定义快捷键”要解决的痛点，靠自定义化解，无法彻底避免，但应提供冲突检测（与另外 8 个一级快捷键是否重复）提示。

### 五、是否延续“命令作为 JS 事件派发”的机制

**建议：继续沿用。** 理由：

- 9 个动作模块的监听端已经接入，沿用可把改动量降到最低；
- 它把“按键捕获”与“动作执行”解耦，新增/调整动作不需要改派发逻辑，符合下载器既有的解耦风格；
- 与现有的 `EVT` 事件系统风格一致。

唯一需要补的就是**派发端**：需求里说的“添加一个模块来专门监听快捷键和派发命令”，应在**内容脚本**里实现（而非 background），直接 `EVT.fire` 即可，不必经由 `tabs.sendMessage` 跨进程转发。

> 附：现有 `ShowLogButton` 自己的 keydown 监听应改为“监听 `commandToggleLogsArea` 命令 + 由集中派发模块负责 `L` 的捕获”，这样 `L` 也能被用户自定义，并让整套机制完整闭环。（`commandToggleLogsArea` 已声明但尚未被使用，正好接上。）

### 六、设置项与模块（no=107，实现时再细化）

按 `notes/添加设置项-add setting item.md` 的流程：

1. `Settings.ts` 的 `XzSetting` 与 `defaultSettings` 增加如 `settings.hotkeys`：对象，键为命令名（`commandToggleSettingsPanel` 等 9 个），值为 `{ key, ctrl, alt, shift, meta }`；默认值保持现有 9 个映射（Alt+X/Z/S/E/P/Q/B/C，以及 L 无修饰键）。
2. `FormType.d.ts`、`FormSettings.ts` 增加对应绑定（该设置可能含多个子控件，按文档处理）。
3. `OptionConfigs.ts` 增加配置项，`no: 107`，位置在 `no: 97` 之后。
4. `OptionsHtml.html` 增加对应 `div.option`（编号 107）。
5. `langText.ts` 增加所需 i18n 文本（设置名、提示、修饰键名称等）。
6. 新增一个**快捷键编辑 UI 模块**：在设置面板里渲染 9 个可编辑项；用户点击某项后捕获下一次按键（含修饰键），实时生成 `{key,ctrl,alt,shift,meta}`，并做两项校验——① 与另外 8 个一级快捷键是否重复；② 是否命中浏览器/OS 保留组合黑名单；校验不通过则提示并拒绝保存。保存写入 `settings.hotkeys`。
7. **集中派发模块**在初始化时读取 `settings.hotkeys` 构建“按键组合 → 命令”匹配表；并监听 `settingChange` 事件，用户改完快捷键后热更新匹配表，无需刷新页面。

在这个设置项里添加一个 `<slot data-name="">` 标签，供编辑快捷键的模块使用。`src/ts/filter/BlockTagsForSpecificUser.ts` 模块就是个使用 slot 标签的例子。
每个快捷键都应该显示对应的作用说明、当前的快捷键值（或“未设置”）、编辑（修改）按钮（使用的图标是 `category-names-line`）、删除按钮（使用的图标是 `close_cancel`）。
点击删除按钮后这个快捷键会被清除，成为没有设置快捷键的状态。
按钮的样式和 hover 状态可以参考 `.blockTagsForSpecificUserWrap .textButton` 的样式。

### 七、结论

- **可行性：高。** 不存在技术阻塞。
- **推荐方案：方案 B**——内容脚本集中 `keydown` 监听 + 派发已接好的 `EVT` 命令事件。
- **额外收益**：该方案同时修复当前 8 个 `Alt+*` 一级快捷键失效的回归问题（监听端已就绪，缺的只是派发端）。
- **主要工作量**：中等，集中在三块新增（派发模块、设置项、编辑 UI）；9 个动作模块无需改动。
- **主要风险点**：仅在于“保留组合校验”与“跨平台修饰键显示”，均可通过编辑 UI 的黑名单校验与平台判断缓解，无底层风险。
- **已确认**：`Alt+E` 对应"手动排除作品"。此前部分注释写作 `Alt+W`，是因为当时采用浏览器 `commands` API 方案、浏览器不允许把 `Alt+E` 设为默认键而临时改动的；现采用方案 B（内容脚本 keydown 派发）不受该限制，已统一改回 `Alt+E`。实现时 `ExcludeWork.ts` 的注释、设置默认值与 i18n 文本都应保持 `Alt+E` 一致。

## 实施方案

> 基于可行性分析（方案 B：内容脚本集中 keydown 派发 EVT 命令）与第 6 章补充（slot 编辑 UI）。按"基础设施 → 编辑 UI → 派发端 → 闭环修复 → 编译验证"的顺序推进，改动面集中在三块新增与少量接线。

### 1. 设置项基础设施（no=107）

#### 1.1 `Settings.ts`
- **类型定义**：在 `XzSetting` 接口（约 225 行，`blockTagsForSpecificUser` 相关项之后）新增 `hotkeys: HotkeyMap`。定义 `HotkeyCombo = { key: string; ctrl: boolean; alt: boolean; shift: boolean; meta: boolean }`（`key` 为 `ev.code`，未设置时为空字符串），`HotkeyMap = Partial<Record<CommandName, HotkeyCombo>>`（这两个类型可放在本文件或 `store/StoreType.ts`，参照 `BlockTagsForSpecificUserItem` 的写法）。
- **默认值**：在 `defaultSettings`（约 765 行之后）新增 `hotkeys` 默认映射，对应 9 个命令的现有键位：Alt+X / Alt+Z / L(无修饰) / Alt+S / Alt+E / Alt+P / Alt+Q / Alt+B / Alt+C。
- **读写方式**：`hotkeys` 为对象型设置，由编辑 UI 模块通过 `setSetting('hotkeys', ...)` 直接写入并触发 `settingChange`；不进入标准表单控件的双向绑定（与 `blockTagsForSpecificUser` 一致），因此 `FormType.d.ts` / `FormSettings.ts` 通常**无需改动**（仅当编译报类型缺失时再补）。

#### 1.2 `OptionConfigs.ts`
- 在 no=97 配置对象之后（约 1408 行）、no=98 之前，插入 no=107 配置项（字段结构参照 1397–1408 行的 no=97 项）：
  ```ts
  {
    no: 107,
  ```

## 录制快捷键的工作细节

录制快捷键由 `src/ts/setting/HotkeyEditor.ts` 的 `startRecord` 方法实现。下面记录其完整工作流程、规则与边界情况。

### 进入录制态

- 用户点击某一行「修改」按钮（图标 `category-names-line`）即进入该行的录制态。
- 进入后，该行的 `.value` 变为蓝字「请按下快捷键」，并显示「Esc 取消」提示按钮（`.escCancel`，平时隐藏，`finish()` 时移除 `.recording` 类就会隐藏）。
- 同一时刻只允许录制一个快捷键：用 `this.recording` 标志控制。
- 进入录制时调用 `setHotkeyRecording(true)`，通知派发端 `HotkeyListener` 暂时停止派发所有一级快捷键命令，避免录入的按键误触发既有动作（例如录入 `Alt+X` 时不会弹出设置面板）。退出录制时调用 `setHotkeyRecording(false)` 恢复。

### 按键的捕获与「主键 / 修饰键」分别处理（核心规则）

快捷键在物理上是两次独立的 `keydown` 事件（先 modifier、后主键），用户不可能让两者"同时按下"。因此录制逻辑**不会在第一次按键后就结束**，而是：

1. 用 `collected` 对象累计每一次 `keydown` 时的修饰键状态（`ctrl / alt / shift / meta`）。
2. 仅当按下的是「主键」时才组装组合并结束录制；单独按下修饰键只更新 `collected` 并继续等待。

这样无论用户"先按住 Alt 再按 X"还是"先点一下 Alt 再点 X"，最终都能正确得到 `Alt+X`。

在录制组合键时，必须先按下修饰键。如果先按 `X`（主键）就只会记录 `X`，并结束录制。后续按 `Alt` 无法补上。这是符合直觉和习惯的（即组合键要先按下快捷键来触发），所以无需特别处理。

**主键识别**：排除单独的修饰键（`ShiftLeft/Right`、`ControlLeft/Right`、`AltLeft/Right`、`MetaLeft/Right`）以及以 `OS` 开头的键，其余视为主键。主键一律使用 `KeyboardEvent.code`（如 `'KeyX'`、`'Digit1'`），**不使用 `ev.key`**，以避免输入法、键盘布局（如 AZERTY、日文假名）带来的差异。

**修饰键状态合并**：最终组合里每个修饰键布尔值是「本次累计值（`collected`）」与「主键按下那一刻 `ev` 上读到的值」的"或"——因为用户可能在按下主键盘字母之前早已松开修饰键，也可能一直按住，两种习惯都要兼容。

### 取消录制（三种方式，均不保存）

录制途中可以随时取消，恢复该行原显示：

1. **按下 `Esc`**：在 `handler` 内优先判断 `ev.code === 'Escape'` 即取消。
2. **窗口失焦（`blur`）**：切走标签页/窗口时自动取消，避免录制态卡死。
3. **点击页面任意区域（`pointerdown`）**：覆盖鼠标与触摸。这对应"用户不知道有 Esc、而是尝试点空白处来取消"的直觉；「Esc 取消」提示按钮本身也靠这个机制取消（点击它即触发 `pointerdown`）。

> 起始那次"点击编辑按钮"产生的 `pointerdown` 不会误触发取消——监听器是在 click 事件派发中途注册的，不会作用于已经发出的事件。

### 校验规则（通过后才保存）

主键按下、组装出组合后，依次做两项校验：

1. **重复校验（`findConflict`）**：遍历其余 8 个一级快捷键，若与某个已设置命令的组合完全相同（`sameCombo` 比较 `key + 四个修饰键`），则弹「快捷键冲突提示」（文案内会带出占用该键的命令名，如 `你要设置的快捷键已被"快速下载当前作品"占用…`），**不保存**该次录入。
2. **浏览器/系统保留组合校验（`isReserved`）**：当组合是「仅 Ctrl、无 Alt/Shift/Meta」且主键命中以下任一，拒绝保存：
   - `Ctrl+T / W / N / R / Q / P / L / K`、`Ctrl+Tab`（浏览器用于关闭/新建/切换标签、刷新、下载、隐私窗口等）
   - `Ctrl + 数字`（用于切换标签）
   这些组合根本不会把 `keydown` 送达页面，设了也无法触发，属于平台限制，故在录入时就拒绝。

> 校验失败时先调用 `finish()` 退出录制态、再弹错误提示、最后 `refreshItem` 还原显示，本次录入不写入 `settings.hotkeys`。

### 保存与存储结构

通过校验后：

- 以 `map = { ...settings.hotkeys }` 拷贝现有设置，把当前命令对应的组合写入 `map[command]`，再 `setSetting('hotkeys', map)` 合并保存（不覆盖其他命令）。
- 弹出「已修改」提示并 `refreshItem` 刷新该行显示。
- 存储结构统一为：
  ```ts
  { key: string, ctrl: boolean, alt: boolean, shift: boolean, meta: boolean }
  ```
- **单键也支持**：如 `L` 即 `{ key:'KeyL', ctrl:false, alt:false, shift:false, meta:false }`。这是方案 B（内容脚本 keydown 派发）相比浏览器 `commands` API 的优势——后者不允许单键作为快捷键。
- 保存后 `settingChange` 事件触发 `HotkeyListener` 重建匹配表，改键**即时生效、无需刷新页面**。

用户修改快捷键后，`src/ts/HotkeyListener.ts` 会立即更新自己保存的快捷键列表的映射，所以无需刷新页面即可生效。

### 删除快捷键

点击某一行「清除」按钮（图标 `close_cancel`）调用 `deleteHotkey`：从 `settings.hotkeys` 删除该命令对应的键、保存、刷新该行显示「未设置」，并弹「已清除」提示。删除后该命令变为"未设置"状态，不再响应任何按键。

### 重置所有快捷键

列表底部「重置所有快捷键」按钮（`_重置所有快捷键`）调用 `setSetting('hotkeys', { ...defaultHotkeys })`，把所有命令恢复为默认值。点击该按钮时会先显示确认弹窗。

### 显示规则（`formatCombo`）

存储结构统一，显示时按平台转换：

- 主键名由 `ev.code` 转换：`KeyX → X`、`Digit1 → 1`，其余原样显示。
- **Mac（按 `navigator.platform` 判断）**：修饰键显示为特殊符号 `⌘ ⌥ ⌃ ⇧`，且符号之间不加分隔符（如 `⌥X`）；`meta/⌘` 在所有平台都显示为 `⌘`。
- **其他平台（Windows / Linux）**：修饰键显示为文字 `Ctrl / Alt / Shift`，各修饰键与主键之间用 `+` 连接（如 `Alt+X`）。

### 录入时的事件处理细节

- 录制期间的 `keydown` 监听使用**捕获阶段**（`addEventListener('keydown', handler, true)`），并在 `handler` 内 `preventDefault() + stopPropagation()`，阻止浏览器对保留组合（如 `Ctrl+T`）的默认行为把页面带走。
- 同一时刻只可能有一个录制 handler：`pointerdown` / `blur` / 另一个 `startRecord` 都会被 `this.recording` 标志拦截，避免多 handler 互相干扰或更新错行。
